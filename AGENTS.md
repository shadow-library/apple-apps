# Agent guide — apple-apps

Read `README.md` first; it covers layout, modules and tasks.

## Rules

- Never commit or hand-edit `*.xcodeproj`, `*.xcworkspace` or `Derived/`. Change the Swift manifests and run `tuist generate --no-open`.
- Every app's `Project.swift` goes through `Project.app(...)`. Build settings belong in `Tuist/ProjectDescriptionHelpers/Settings+Shadow.swift`, never per app (capability-derived settings are built in `AppCapability.swift` and merged there); settings of the package targets (ShadowKit, product kits) live in `Tuist/Package.swift`'s `PackageSettings`.
- Store-build options are read only by `BuildEnvironment` from `TUIST_*` variables (`TUIST_MARKETING_VERSION`, `TUIST_BUILD_NUMBER`, `TUIST_USES_NON_EXEMPT_ENCRYPTION`, `TUIST_UNRESTRICTED`), unset meaning the development build; never hard-code a version, a build number or `ITSAppUsesNonExemptEncryption`, and add a new option to `Scripts/check-build-options.swift` (`mise run check:build-options`).
- `SHADOW_UNRESTRICTED` is defined only on the `NovelForgeCore` target (`SettingsDictionary.novelForgeCore` in `Tuist/Package.swift`) and read only by `UnrestrictedWriting.isAvailable`; never define it on an app target or another module.
- An app's category comes only from `Project.app(category:)` (`AppCategory`) and its icon only from `Resources/Assets.xcassets/AppIcon.appiconset` (opaque, since iOS refuses alpha); pass `accentColor: true` only with an `AccentColor` colour set.
- An app's home-screen and menu name comes only from `Project.app(displayName:)` (`CFBundleDisplayName` and `CFBundleName`), checked by `mise run check:build-options`.
- Every identifier is reverse-DNS under its owner: `com.shadow.apps.<app>` for an app (bundle id, keychain services, defaults keys) and `com.shadow.library.<library>` for a shared library (bundle id, migration identifiers, format tags, hash domain separators). A new library target is added to the list in `Tuist/Package.swift`.
- Depend on shared modules with `.shared(.<module>)`, never `.external(name:)` with a string.
- Depend on product modules with `.product(.<module>)` (`ProductModule`), never `.external(name:)` with a string.
- Code reused by a second app belongs in `Packages/ShadowKit`, not copied between apps; app code (vault, sync and AI screens) goes in `ShadowAppShell`, which takes the app's `AppIdentity` and never names an app, its id or its vault word. Keychain and defaults names derive from `AppIdentity` and never change formula.
- `ShadowAppShell`'s user-facing strings live in its own catalogs (`Resources/*.xcstrings`, `bundle: .module`, app words as `%@`, no `extractionState`), which an app never edits; a public shell view puts `\.appIdentity` in its environment.
- Every app passes its own `requestGuard` to `AIServices.live` and `AIServices.demo`; the shell has no default.
- The unrestricted model field is offered only through `AIServices.live(offersUnrestrictedModel:)`, from the app's build flag (`UnrestrictedWriting.isAvailable` in Novel Forge).
- Every gate that holds an AI action for a provider, and `aiProviderSheet`'s continuation, ask `AIServices.isReadyForStandardCalls` (a usable provider and, for OpenRouter, a model for at least one pace); an action that is not ready presents `aiProviderSheet` before anything is sent and goes on only from its `onConnected` (never after the owner chose the demo); in Novel Forge a job asks only when it would start on this device (`isReady(toStart:on:)`, `ProviderGate` for job-line actions).
- OpenRouter sign-in goes only through `AIServices.signInWithOpenRouter` (PKCE S256 plus `state`) with `AppIdentity.openRouterCallback`, whose scheme `ASWebAuthenticationSession` catches; never register it in an Info.plist.
- Provider keys are written only through `AIServices.saveKey`/`removeKey`, which bump `keysRevision`; never through `AIServices.keys` directly.
- OpenRouter's model list is fetched only while OpenRouter is the chosen provider (`AIServices.loadOpenRouterModelsIfChosen` through `loadsOpenRouterModels(_:)` on a window root, `AISettingsModel.loadModelsIfChosen` from a models section on screen) or when an OpenRouter key is saved; never at launch or on opening a screen while another provider is chosen.
- Scripted answers ship only as `DemoModelProvider` behind `AIServices.demo` with the app's `DemoScript`: it reads and saves no key, sends nothing and refuses unrestricted calls, and its consent disclosures keep the owner's disclosure ids and say nothing leaves the device.
- A demo runs only through `DemoSession`, with its own vault in `DemoDirectory` and device choices only in `DemoDefaults` (screens pick them from `MemoirScreenContext.defaults` or `AIServices.isDemo`); the window takes its vault and runtimes only from `NovelForgeWindowRuntimes`/`MemoirWindowRuntimes.active`, and every scene phase also reaches the owner's set. A demo never schedules reminders, imports Health, attaches sync or exposes vault deletion or worker designation.
- Demo content and scripts live in the product core (`NovelForgeDemo`, `MemoirDemo`; Memoir's receipt rule in the app beside its schema); every scripted structured reply has a test validating it against its real schema, schema names come from the shared constants, and a `DemoMatch.phrase` must be absent from the prompt the core builds around the author's words.
- `AppIdentity.privacyPolicyURL`, `supportURL` and `contactAddress` stay nil until the page or mailbox exists; About shows a row only for a value `AboutLink.links(for:version:)` accepts.
- Every `AboutDisclosure` line must be true of every build, route and device (worker runs, OpenRouter's onward routing, iCloud Keychain); a change to what leaves the device updates the app's About lines, its consent disclosures and its privacy manifest together.
- `THIRD_PARTY_NOTICES.md` and `ShadowAppShell`'s `Resources/ThirdPartyNotices.md` change together (a test compares them); a new third-party dependency adds its notice to both.
- Diagnostics never carry content, keys, tokens, locations, vault ids or names that identify the owner: an app's `DiagnosticsSources` summary holds only counts, flags and codes (`DiagnosticsValue`), `SyncRunRecord` only counts, instants and error codes, and a change to `summary.json`'s shape raises `DiagnosticsSummary.currentVersion`.
- A log argument diagnostics shows (text logged `.public`, a number logged without a privacy marker) is only a code, count, kind or state, never owner content, a key, a path, a location, a vault id or a name.
- An error a shell screen presents with its code adopts `DomainFailure` (`ShadowStore`) where it is declared, never retroactively in an app.
- A product's core lives in `Packages/<Product>Kit` (first: `Packages/NovelForgeKit`, module `NovelForgeCore`). It imports no UI framework (SwiftUI, UIKit, AppKit) and reaches ShadowKit through the package's products.
- Capabilities (iCloud, push, background modes, keychain group, camera, Mac sandbox, continued processing, HealthKit) are declared only through `Project.app(capabilities:)` with `AppCapability`; never write entitlements, `aps-environment`, `UIBackgroundModes` or usage strings by hand. Capabilities that need a signing team are emitted only when `TUIST_DEVELOPMENT_TEAM` is set, so team-less builds must keep working.
- `aps-environment` stays `development` in every configuration; never make Release `production`, since a development-signed Release build would fail and exporting for App Store Connect takes the distribution profile's value.
- Each app that reaches a required-reason API ships `Apps/<App>/Resources/PrivacyInfo.xcprivacy` (no tracking, no collected data types); a new call to a listed API, in the app or any module it links, adds that category with Apple's reason to every linking app's manifest and to `Docs/privacy-manifests.md`, and `mise run privacy:check` must pass.
- HealthKit is iOS only and read-only: its entitlements go only through `CODE_SIGN_ENTITLEMENTS_CONTENTS[sdk=iphone*]`, and app code reads `ShadowCapabilities.HealthKit` as granted only when it is the string `YES`. In Memoir, `HealthKit` is imported only in `Health/HealthKitSampleSource.swift` (one shared `HKHealthStore`), imports run only through `HealthImportRunner` on the designated reader, and the designation changes only through `HealthReadingModel` (`HealthSettings.claim`/`release`).
- `ShadowTestSupport` is for test targets only; never link it into an app target.
- Third-party dependencies are added to `Tuist/Package.swift` (for apps), `Packages/ShadowKit/Package.swift` (for shared modules) or the product package's own `Package.swift` and need the user's approval.
- `ShadowDesignSystem`: use semantic tokens only (`ShadowColor`, `Spacing`, `Radius`), never primitives or literal colours; the library has no user-facing strings.
- Glass goes on the navigation layer only (bars, sidebars, menus, popovers, sheets), never on content. Use `.shadowGlass` and `ShadowGlassGroup`, never a hand-drawn effect.
- Tokens come from `Design/tokens.json`; run `mise run tokens` and never edit `Tokens/Generated/`.
- Each app area owns its own `<Area>.xcstrings` and never edits another's. A plural variation key written as `%#@name@` takes later arguments by explicit position (`%2$@`, `%2$lld`); an unnumbered specifier after it crashes at run time.
- `@_spi(Preview)` is for preview and capture hooks (Catalog, screenshots), never for app code.
- Novel Forge schema v1 is frozen: adding kinds or fields raises `NovelForgeSchema.version` and saves `Fixtures/schema/registry-v<N>.json` beside v1; never reorder or rename hashed key components.
- Memoir's core is `Packages/MemoirKit` (module `MemoirCore`): kinds prefixed `mm_`, local tables `mm_local_*` under the same rules as `nf_local_*` (the replay ones are dropped with the projection's layout and rebuilt when the vault scope is cleared), identifiers under `com.shadow.library.memoircore`. Stores open only through `MemoirStore.open`/`MemoirStores` and are written only through `MemoirStores.store(of:)` and the typed records in `MemoirCore/Records`.
- Memoir registries are frozen per store: adding kinds or fields raises that store's version in `MemoirSchema` and saves `Fixtures/schema/[<store>-]registry-v<N>.json`; never reorder or rename `MemoirKey` components.
- Memoir calendar dates are `LocalDate` (integer civil days); only `IssueClock` reads the device's time zone, when a command is issued, and commands and the replay horizon carry the zone in force on the day the account has reached (or the staged zone once that day has passed). The app takes that clock for commands, the replay horizon and day turns only from `AccountZone` (`MemoirClock`); the device's zone governs only before the account has one.
- Memoir commands are built from a `MemoirCommandBody` through `CommandIssuer` (the content overload when the command names a record). A payload never carries the owner's words, a measured value or a threshold of an activity- or health-class metric; extend `MemoirCommandKind.integerPaths` only with outcome-class integers at a per-type path, and add even an optional payload field only with a new ruleset version.
- Hero state is derived only through `Replay.run`/`step`/`extend`, which read only a command's recorded instant, offset, `issuedOn` and ruleset version; a command replay cannot read halts it, and a horizon-walked state is a view, never a checkpoint: checkpoints come only from `Replay.step`'s day-closing boundary.
- Memoir derived state is the replay projection (`MemoirReconciler`, `Projection/`, passed as `projection:` when the main store opens): `mm_derived_*` tables are written only from a `ReplayState` and read through `MemoirDerived`; raise `MemoirReconciler.replayVersion` when replay's meaning changes or a new `mm_derived_*` table joins `DerivedRows`, and `ReplayState.codingVersion` when its encoding changes.
- Health imports go through `HealthImport` and issue no command; whether Activity syncs through iCloud comes from `HealthSettings` via `MemoirSyncRouting`.
- Insight model calls go only through `InsightStepContext.call`, insight job keys through `InsightJobAddress`/`InsightJobKind` and origins from `InsightJobOrigin.json`; an insight context reads journal text only under `journal_reflection_reason` consent and activity or health data only under health consent, and the insight path never issues a command.
- Memoir screens take one `MemoirScreenContext` (`init(context:)`) and write only through its `MemoirWriter` (`issue`, `issue(_:text:creating:)` for a general-class record, `write`, `quickLogs`, `metrics`); app code never builds a `CommandIssuer` itself, MemoirCore writers take a `CommandIssuerSource` resolved inside each write, only `MemoirDayTurns` runs `ProjectionDayTurns`, and write failures are shown through `WritingErrors.presented` (nil for a cancelled write).
- Memoir screens take derived values (quest and hero state, money totals, log summaries, reflect statistics) only from MemoirCore's read models in `Reads/` (the `ReplayReadModel`s through `load`/`observe`, `MoneyReads`/`MoneyBook`, `LogReads`, `ReflectReads`), never computing them in the app, running replay or reading `mm_derived_*`. An action a board offers must agree with replay (`ReadAgreementPropertyTests`, whose policy list names the client-only blocks); quest actions go only through `QuestActionsModel.perform`, and `quest.deleteLog` is issued only as the reference's Undo.
- Memoir expenses are created, edited and deleted only through `ExpenseEdits`, and subscriptions only through `SubscriptionWrites` (record and command in one write); typed amounts are read only through `AmountInput` with `AmountFormat(locale:)`, and money is shown from minor units with the currency's ISO 4217 places (`MoneyText`).
- A receipt image enters a store only through `ReceiptWrites` (the blob put first, then one write of the `ReceiptRecord`, the expense and any `receipt.scan`) while the expense is first saved; structuring sends only the recognised text, under `memoir.receipt_text` consent, never the image.
- Memoir reminders are scheduled only by `ReminderScheduler` from `ReminderReads.observePlan` through `ReminderPlan.diff`, and it removes only identifiers under `Reminder.identifierPrefix`; "Remind me on this device" is per device, and hosted tests use `InertReminderNotifications`.
- Memoir insights start only in the foreground through `MemoirInsights` (one `InsightEngine` and the shell's `CostSettler` per vault); the Ask screen reads `InsightRequests.listing` and reads again at its `changesAt`, and stops or asks again only through `InsightEngine.cancel(job:)`/`retry(job:)`.
- Weekly review answers live only in `mm_local_review_*` through `WeeklyReviewAnswers`, stay on the device, and never write a week that has ended.
- Memoir onboarding shows only while the main store has no `AccountSettingsRecord` and no command, waits while sync is bringing data or a key, and writes its settings, first zone and first quest in one write stamped in the chosen zone; the home currency is set once, when the settings record is created. Its first step offers the demo, which writes nothing to the owner's vault.
- A Memoir vault is deleted only through `MemoirVaultDeletion`: detach the primary first, then close the stores inside `VaultModel.reopen(after:)`, never removing an open store's files. Device-local Memoir defaults live under `com.shadow.apps.memoir.*` and are cleared with the vault, except the shell's `.ai.*` and `.sync.*` keys. The export's shape is `MemoirExportFile`; changing it raises `currentVersion`.
- Write Novel Forge data through the typed records in `NovelForgeCore/Records` (their create, edit, revise and append writes), never by setting raw JSON fields on a `WriteTransaction`.
- Derived state lives in a `Derivation` on the `Projection` frame, in `Reconcile/<Area>/`: `.records` inputs map from the `EntityRef` alone, per-novel aggregates over hash-keyed kinds subscribe through `RecordIndexDerivation` (or through `.outputs(of:)` of their own per-ref layer whose rows record the novel and chapter), and `key(of:)`, a one-key `request(for:)` and a primary key are mandatory.
- Local unsynced Novel Forge tables are named `nf_local_*`, created with `CREATE TABLE IF NOT EXISTS` by the write that first needs them, read only after a `tableExists` check, and cleared with their owner (`ChatLocalCleanup`, `ChatTurnRecords.forgetOrphans`, `PendingActions.forget`) so a deleted session, novel or proposal leaves nothing behind.
- App code builds proposal apply and revert contexts only through the public narrow inits (`ProposalApplyContext(novel:now:ageGate:)`, `ProposalRevertContext(novel:now:ageGate:)`); whether unrestricted writing is available is `UnrestrictedWriting.isAvailable` (the `SHADOW_UNRESTRICTED` build flag) narrowed by this device's `AgeGate`, never widened by a caller. The Novel Forge app keeps the gate only in `AdultConfirmationModel` (the day it was confirmed, per device, never a birth date, never synced), hands that one `AgeGate` to `ChatTurnEngine`, `JobEngine` and `NovelContext`, and offers unrestricted writing only through `UnrestrictedOffer.decide` (build, assigned model, `HardLineCoverage`, gate).
- Register every derivation in the incremental == rebuild harness (`Tests/NovelForgeCoreTests/Projection/ProjectionHarness.swift`); raise its `version` when `outputs(for:in:)` changes meaning.
- Fixtures come from `bun` generators that import the reference read-only; they are deterministic and hold no machine paths. Never write inside the reference checkout.
- Port JavaScript semantics through `ShadowText` (`Packages/ShadowKit/Sources/ShadowText`, with `Regex/`); never use `NSRegularExpression` or Swift `Regex` for a pattern taken from the reference.
- A remote storage provider lives in its own `ShadowSync<Name>` module that depends on `ShadowSync` (plus `ShadowNetworking` when it speaks HTTP), never inside `ShadowSync`; one that signs in with OAuth uses `OAuthSession`.
- Sync files are deleted only by the rules in `ShadowSync` (`SyncCompaction`, `SyncAdoption`, `RecoveryCopies`, and `SyncBlobCollector` for blob parts), by recorded names and never by prefix; never hand-delete under `replicas/` or `blobs/`.
- A record names a blob only by its `BlobID.description`, verbatim, in a synced field of the store whose `VaultBlobs` put it; a store's blobs live only in its `blobDirectory`.
- CloudKit is imported only in `ShadowSyncCloudKit`; everything else reaches it through the `CloudKitZoneClient` seam.
- A product's registry is built through `SyncKernelSchema.registry(version:adding:)`; app kinds never start with `_`.
- A store holding health- or activity-class kinds is opened with `backup: .alwaysExcluded` in its own directory and synced only through a provider whose class policy admits them; a product's main store admits only `[.general]`. One refused change stops a store's whole upload, so never declare a kind in a store whose provider refuses it.
- App code syncs a vault only through `SyncRuntime` (start, foreground, background, localWrite, changeNotice, attach, detach, move, stop, keysImported, keyServices and fetchBlob calls), never by driving `SyncEngine`, `SyncStartup` or a `SyncAttachment`, and hands it local writes from `VaultStore.loggedChanges()`, never from write call sites.
- A store beyond a product's main one syncs only as a `SyncStoreRoute` declared in `SyncedVault.declaredRoutes` and named by its routes closure; a route's name is stored layout (Memoir: `activity`, `health`). Only the primary runtime attaches, detaches, moves and serves key screens; a vault that declares routes neither moves nor follows a move (`routedStoresUnsupported`), and a route stops only through `SyncRuntimes`. Apps add to Sync Settings only through `.syncSettingsSection`.
- Sync locations are saved only by `SyncLocationStore` (outside every vault directory); a saved location is never replaced by another one automatically (only `SyncWiring` renews a stale folder bookmark in place). A local folder's bookmark comes only from `LocalFolderAccess`, and the folder is never inside the app's own data.
- A vault is created only by `VaultSetup.create()` (ring key inserted before `vault.json`); never write `vault.json` or ring keys by hand.
- Sync secrets live only in the stores from `SyncSecureStores` (ring keys and S3 credentials synced; device marker and OAuth tokens this-device only); never log or describe one. A recovery phrase is never stored: an app keeps at most its recipient id, and shows the words once, uncopyable and hidden while the scene is inactive.
- A keychain that refuses the build (`errSecMissingEntitlement`) is `keychainUnavailable`, never a generic failure; hosted keychain tests skip on it with a recorded reason.
- App code learns its restricted capabilities only from the `ShadowCapabilities` Info.plist dictionary `Project.app` writes; never create a `CKZoneClient` or register for remote notifications without it.
- Never yield or finish an `AsyncStream` continuation while holding a lock its `onTermination` also takes.
- Pipelines call models only through `JobStepContext.call` or `callText`, which apply the route, the hard-line screens and the ledger.
- Job keys are built and read through `NovelJobAddress` and `NovelJobKind`, never by string.
- A job's `origin` comes from `NovelJobOrigin.json`.
- The vault's worker is written only through `WorkerRecords.designate` (`JobEngine.designateWorker` in Novel Forge, `WorkerModel` in the app) and read only as `VaultWorker` (`worker()`, `observeWorker()`, `WorkerBacklog`, `JobPlacements`), never from the `jobs_worker` record; an app adds `JobSchema.workerEntities` only with a new registry version.
- Whether a job runs on its requester or the worker comes only from `NovelJobKind.queuesForWorker` and, in the app, `JobPlacementPolicy`.
- Stop a run on purpose only through `AttemptRunner.interrupt(_:releasingLease:)` (`JobEngine.interrupt(job:releasingLease:)`), never by cancelling its task; hand a job between devices only through `interrupt`, `resumeHere` and `settleStoppedAttempts`.
- An automatic attempt yields to another device's live attempt started by hand (`AttemptRecord.yields(to:)`); never add a path that starts or resumes one beside it.
- Lease liveness is decided at read time against a `now`, never stored in a derived row; a read model that depends on it returns `changesAt`.
- A Novel Forge pipeline declares its `PipelineCourse`, which is read only for progress.
- Continued processing goes only through `JobRunHost` (`ContinuedProcessingHost` from `JobRunHosts.system()`): only `.person` runs are submitted, the wildcard is registered once per process, and the expiration handler awaits `interrupt` only within a bounded deadline, then completes its task.
- The Mac login item is registered only when the user turns worker mode on, never at launch; hosted tests never touch real defaults or `SMAppService`.
- Derived ids use `derivedID(_:_:)` with a `com.shadow.library.<library>.<purpose>` domain.
- New test suites take a `TestTimeLimit` tier (`quick`, `standard`, `property`), never a literal limit.
- Tests are named `should…`; Swift Testing tests that resolve `Color` or `Font` need `@MainActor`.

## Verifying a change

- Packages: `mise run test:packages` runs every package — fastest loop, needs no generation.
- Apps: `mise run bootstrap && tuist test <Scheme>`; add `--platform macOS` if simulators are unavailable.
- Use `--no-selective-testing` with `tuist test`, or unchanged targets are skipped. CI passes `--skip-ui-tests` on macOS and visionOS.
- `mise run screenshots` and anything touching simulators or the window server needs the command sandbox disabled, or it hangs.
- After changing `BuildEnvironment`, `Project+App.swift` or `Tuist/Package.swift`'s settings, run `mise run check:build-options`.
- Always finish with `mise run lint` (which ends with `privacy:check`) and `mise run lint:graph`.

Tuist requires the repository to have at least one commit; `tuist generate` fails on a fresh `git init`.
