# Shadow Library — Apple Apps

Monorepo for every Shadow Library app on Apple platforms (iOS, iPadOS, macOS, watchOS, tvOS, visionOS) and the Swift packages they share.

## Requirements

- Xcode 27 (Swift 6.2+)
- [mise](https://mise.jdx.dev) — pins Tuist and runs the repo tasks: `brew install mise`

## Getting started

```sh
mise install          # installs the pinned Tuist
mise run bootstrap    # resolves packages and generates ShadowLibrary.xcworkspace
open ShadowLibrary.xcworkspace
```

Xcode projects and the workspace are generated from Swift manifests and are never committed. Re-run `tuist generate` after changing any
`Project.swift`, `Tuist/Package.swift` or helper; adding or removing source files does not need it, since targets use buildable folders.

To sign for devices, export your team before generating: `export TUIST_DEVELOPMENT_TEAM=ABCDE12345`.

## Layout

```
Apps/                         one folder per app, each with its own Project.swift
  Catalog/                    design-system gallery; also the pipeline's smoke test
  NovelForge/                 Novel Forge for iPhone, iPad and Mac (`.phoneAndMac`); vault opening and the library shell
  Memoir/                     Memoir for iPhone, iPad and Mac (`.phoneAndMac`); vault opening and the navigation shell
Packages/
  ShadowKit/                  the shared Swift package (one library product per module), with the app shell every app reuses (`ShadowAppShell`)
  NovelForgeKit/              Novel Forge's core (`NovelForgeCore`): domain rules, pipelines, retrieval; no UI
  MemoirKit/                  Memoir's core (`MemoirCore`): calendar, rules, records, replay; no UI
Docs/                         checklists run by hand on real devices
Tuist/
  Package.swift               external + local package dependencies for the apps
  ProjectDescriptionHelpers/  Project.app(...), shared settings, platform presets
  Templates/app/              scaffold used by `mise run new-app`
Tuist.swift  Workspace.swift  mise.toml  .swift-format
```

Bundle identifiers: apps are `com.shadow.apps.<app-name>` (lowercased, test targets add `.tests` / `.uitests`) and shared libraries are `com.shadow.library.<library-name>`.

Capabilities are declared only through `Project.app(capabilities:)` (`AppCapability`): `iCloud`, `pushNotifications`, `keychainSharing` and `healthKit(usage:backgroundDelivery:)` need a signing team and are left out of a team-less build; `remoteNotificationBackgroundMode`, `camera(usage:)`, `macSandbox` and `continuedProcessing(context:)` do not. `continuedProcessing(context:)` writes `BGTaskSchedulerPermittedIdentifiers` with `<bundle id>.<context>.*` for iOS (the key also lands in the Mac slice of a multiplatform target, which ignores it) and no background mode, since Apple documents none for continued processing (only `processing` for `BGProcessingTask` and `fetch` for `BGAppRefreshTask`). Background modes from every capability are merged into one `UIBackgroundModes` array; Xcode empties that array in a Mac build. `healthKit` is iOS only and read-only: it writes `NSHealthShareUsageDescription` (no update string, since the app never writes to Health) and `HealthKit` under `ShadowCapabilities`, the string `YES` in an iPhone or iPad build signed with HealthKit and `NO` in the Mac slice (the other entries are booleans; read this one as true only when it is `YES`), and its entitlements (`com.apple.developer.healthkit`, plus `.background-delivery` when asked) go through `CODE_SIGN_ENTITLEMENTS_CONTENTS[sdk=iphone*]`, which Xcode merges over the shared entitlements file for iPhone and iPad builds only, so the Mac slice never carries them.

`VaultStore.open` on a file sets file protection `completeUntilFirstUserAuthentication` on the vault directory and on the database, `-wal` and `-shm` files, and fails with `StoreError.fileProtection` if it cannot (macOS has no such protection and skips it; in-memory stores are untouched). `SyncEngine.start()` (or `StorageAttachment.attach(_:)`) flags the vault directory as excluded from device backups, `StorageAttachment.detach(_:)` clears it, and a failure there is reported (`SyncEngine.backupExclusionFailure`, a log entry) without failing the attach (attach is idempotent and re-asserted on every start; clearing the flag is eventually consistent on macOS; a vault directory must hold only the vault's own files, the database with its `-wal`, `-shm` and `-journal` files and its process locks such as `<db>-jobs.lock`, or the flag is refused), since the flag is only guidance and the replica self-check carries correctness.

The OAuth client in `ShadowNetworking/OAuth` is the authorization-code flow with PKCE for public clients and has no UI: `OAuthClient.beginAuthorization()` returns the address to open and a pending authorization (verifier and state), `completeAuthorization(callback:pending:)` checks the redirect, the state and any provider error and exchanges the code, and `refresh(_:)` keeps the old refresh token when the server does not rotate it. `OAuthSession` hands out access tokens through an `OAuthTokenStore`: it refreshes ahead of expiry, shares one refresh among concurrent callers, saves rotated tokens before returning them, and after a 401 refreshes once per rejected token (`refreshAfterRejection(of:)`). `invalid_grant` becomes `OAuthError.reauthorizationRequired`. Presenting the system sign-in sheet is the app's job. Client ids and redirect URIs are inputs from the app, never constants.

`RecoveryPhrase` (`ShadowSync/Keys`) encodes a 256-bit `RecoverySecret` as 24 BIP-39 English words (the entropy plus the first 8 bits of its SHA-256 as checksum; no passphrase or seed derivation) and parses them back after NFKD normalisation, lowercasing and whitespace collapsing, throwing `RecoveryPhraseError` (`wrongWordCount`, `unknownWord(position:)`, `badChecksum`); it prints as `RecoveryPhrase(redacted)`. The word list is `RecoveryWordList.swift`, generated and never edited: save `bip-0039/english.txt` from `bitcoin/bips` and run `swift Packages/ShadowKit/Scripts/generate-recovery-word-list.swift <english.txt> Packages/ShadowKit/Sources/ShadowSync/Keys/RecoveryWordList.swift`, which refuses a file whose SHA-256 is not the pinned `2f5eed53…dbda`.

Novel Forge uses `ShadowSyncCloudKit` and `ShadowSyncS3`; `ShadowSyncOneDrive` and `ShadowSyncGoogleDrive` stay package-level until it has their app registrations. A vault's folder on OneDrive and Google Drive is a `VaultFolderName` (`ShadowSync`), which both accept.

`S3StorageProvider` signs every request with AWS Signature Version 4 (CryptoKit, the payload hash of the whole body) and keeps a vault under the configuration's key prefix; listings skip objects whose names are not object keys, so foreign files in the bucket are ignored. It reports server time from the `Date` header, never pushes change notices (the app polls), and caps an object at 256 MiB. Put-if-absent is atomic (`If-None-Match: *`) only when the configuration says the endpoint honours it, otherwise a HEAD before the PUT that two racing writers can both pass. `probeConditionalWrites()` answers that question by writing the reserved `.shadow-s3-probe/conditional-writes` object twice; it removes only the object it wrote or one a crashed probe left more than 15 minutes earlier (so another device's probe is left alone), throws when the answer is inconclusive, and the caller keeps a true or false answer with `configuration.withConditionalWrites(_:)`. The credentials need list, get, put and delete on the bucket; without list permission S3 answers a missing object with 403, which reads as `unauthenticated`. The live conformance test runs only when `SHADOW_S3_LIVE_ENDPOINT`, `_REGION`, `_BUCKET`, `_ACCESS_KEY_ID` and `_SECRET_ACCESS_KEY` are set (optional: `_SESSION_TOKEN`, `_PATH_STYLE=1`, `_ALLOW_INSECURE_LOCALHOST=1`); it works under a fresh `shadow-live-tests/<uuid>` prefix and deletes what it wrote.

`OneDriveStorageProvider` keeps a vault as the files of one folder, `Apps/<app>/<vault folder>`, each named by `OneDriveName`: `/` becomes `!` and capitals, `_`, trailing dots and names OneDrive reserves are escaped so names stay distinct on a case-insensitive drive, and a key too long for a OneDrive path is stored under a digest with the key written ahead of its bytes. Listings are answered in key order from an index fed only by the folder's delta feed (saved through `OneDriveStateStore`: `InMemoryOneDriveStateStore` or the JSON `FileOneDriveStateStore`; a 410 rebuilds it), so they may lag but never invent a file. It supports put-if-absent (`conflictBehavior=fail`, simple uploads up to 4 MiB, upload sessions in 320 KiB multiples above that), reports server time from Graph's `Date` header, has a change feed but no change notices, takes objects up to 72 MiB (the largest segment payload plus room for its encryption framing) and deletes through `$batch`. Delta on a folder below the drive root is unverified for work and school accounts; if Graph refuses it, listing fails with a lasting error rather than a sign-in prompt, and `.common` stays the default audience until the live test passes with an organisations account. It needs a transport that refuses redirects, so the bearer token never reaches the download host. A Microsoft app registration (client id and redirect URI) does not exist yet. The live conformance test runs only with `SHADOW_ONEDRIVE_LIVE_CLIENT_ID`, `SHADOW_ONEDRIVE_LIVE_REDIRECT_URI`, `SHADOW_ONEDRIVE_LIVE_REFRESH_TOKEN` and `SHADOW_ONEDRIVE_LIVE_VAULT_FOLDER` (optionally `SHADOW_ONEDRIVE_LIVE_AUDIENCE`) set; it works in a fresh vault folder and deletes it afterwards.

`GoogleDriveProvider` keeps a vault as flat files in the hidden app data folder (scope `drive.appdata`): each file is named by its object key and carries the vault name in an app property, and the provider addresses files by id through an index it keeps from the changes feed and saves through a `GoogleDriveStateStore` (`GoogleDriveFileStateStore`, `InMemoryGoogleDriveStateStore`); a first listing takes the feed's start token and then enumerates the folder, enumerating once more two minutes later to add what Drive's search had not yet shown, and a rejected token rebuilds the index; when the token a rebuild just took is rejected before any page succeeds, the provider reports `unavailable` and rebuilds again only after a backoff (one hour, doubling up to a day, kept across restarts and reset once the feed works). Capabilities: no pushes, a change feed, no atomic put-if-absent (an `ifAbsent` put checks the index after catching up), server time from each write, objects up to 72 MiB (the largest sealed segment, with room to spare), any sync class. Drive allows two files with one name; every device picks the same one, the most recently modified (ties to the smallest file id), for reads, listings and overwrites, and an overwrite updates that file and then deletes the others. Objects up to 5 MiB go up in one multipart request, larger ones in resumable 8 MiB chunks. Sign-in needs a Google OAuth client for the app (NEEDS USER; none is registered yet). The live conformance test runs only with `SHADOW_GOOGLE_DRIVE_CLIENT_ID`, `SHADOW_GOOGLE_DRIVE_REDIRECT_URI`, `SHADOW_GOOGLE_DRIVE_REFRESH_TOKEN` and `SHADOW_GOOGLE_DRIVE_VAULT` set, under a fresh vault name, and deletes what it wrote.

`CloudKitStorageProvider` keeps a vault in one zone of the private database (zone `vault-default` by default), one `VaultObject` record per object, named `o-` and the lowercase SHA-256 of `com.shadow.library.shadowsynccloudkit.record-name`, a zero byte and its key, with `path`, `size` and either `bytes` (up to 512 KiB) or `parts`, a list of assets of up to 16 MiB each that is reassembled and checked against `size` on read; objects are capped at 72 MiB. Listings come in key order from an index kept from the zone's change feed and this device's writes, saved by the caller through a `CloudKitStateStore` (`CloudKitFileStateStore` writes backup-excluded JSON and must live outside the vault directory); an expired change token rebuilds it, and an unreadable file rebuilds it while still counting the zone as seen. The index is bound to the iCloud user record it was read under; another account found on the first call or after a sign-in counts as an account switch. It supports put-if-absent, reports the record's modification date as server time and yields a change notice when a push brings changes. A zone it has never seen is created by the first put; a zone found missing by a request sent while it was known, or an account that signed out or switched, stops every call and shows in `condition()` and `conditionChanges()` until the runtime attaches again (`recreateZone()` only after the user agrees). Behind the `CloudKitZoneClient` seam, `CKZoneClient` reads and writes records and the zone's change feed directly on `CKDatabase` (`desiredKeys` keeps listings from downloading assets) and runs a `CKSyncEngine` only for the database subscription, pushes and account events; `FakeCloudKitZone` (`ShadowTestSupport`) stands in for it in tests. Create a `CKZoneClient` only in builds with the iCloud and push capabilities (without the entitlement CloudKit is reported to raise an exception), and at most one per container in a process, since CloudKit's production environment allows one sync engine per database; a second throws `engineAlreadyRunning`. `CKZoneClient` compiles but has never run: it needs the container, the entitlements and the schema deployed. Not confirmed against the service: that a new record saved over an existing name with `.ifServerRecordUnchanged` fails with `serverRecordChanged`; that saving an existing zone succeeds; that an `.allKeys` overwrite clears a field set to nil (reads use `parts` only when their sizes add up, so a stale field is never read); that the sync engine still reports database changes while told to skip the vault zone; and which error follows the user deleting the app's iCloud data.

`VaultStore.observeReads(_:)` reads again after every commit, local or remote; `observeReads(writingTo:_:)` only after a commit with a statement that wrote to one of the named tables, as GRDB's authorizer names them before the statement runs, so `WITHOUT ROWID` tables count.

Every write first checks that the connection is not left read-only: under load a cancelled access has been seen to leave it in `PRAGMA query_only` with no read-only access open, so the next `BEGIN IMMEDIATE` failed with `SQLITE_READONLY`. A write that finds it so turns `query_only` off and logs a notice; the cause inside GRDB is not yet confirmed.

`VaultProcessLock` is an exclusive `flock` on `<db>-jobs.lock` beside the database, for work only one process may do on a vault; the kernel drops it when the process ends, so a crash never leaves the vault held. `Ledger.reconcilePending` looks up the cost of pending OpenRouter calls by generation id (bounded batch, retries with backoff, a grace period for calls still in flight) and stops on an authentication failure.

`ShadowJobs` keeps a job (`JobRequest`: key, payload, an app-owned `origin`, the requesting replica) and its attempts as synced records. An attempt has one writer, the replica that started it; another replica's write is refused (`notWriter`). A running attempt holds a lease (`LeaseTerms`: 6 minutes, renewed by a 2 minute heartbeat, checked against a trusted clock and a skew limit). `JobStatus` is derived from the job and its attempts at a lease instant: queued, running, failed, cancelled or succeeded. `AttemptRunner` (one per vault) runs a pipeline of steps: each step's output commits in one transaction with the attempt's checkpoint, which lives in a table local to the device. That commit is a compare-and-set: it holds only while the saved checkpoint is still the one the step ran from, otherwise `checkpointMoved` and the second process stops. `resumeInterrupted` continues this device's attempts from their checkpoints, and a stop mark settles an attempt whose process ended instead of resuming it (`resumeInterrupted(where:pipeline:)` only those its filter takes); `settleStopped` settles the stop marks, forgets runs whose attempt ended or whose job is gone, and resumes nothing, and `interruptedRuns` lists what this device can resume (attempt, job, step, checkpoint). `interrupt(_:releasingLease:)` ends a run here as a crash would: once it returns the run writes nothing more (a step that ignores cancellation holds it until the step returns, and a stopped run's step can open no new model call), a step commit already under way lands whole, and the checkpoint stays for `resume`; a run carrying a stop mark answers `settling`, since it settles rather than resumes. Releasing the lease writes it expired at this device's lease instant, so another replica's automatic attempt may start at once; a replica whose clock is behind reads it live until its own clock passes that instant. `AttemptVerdict` decides who goes on: an attempt started by hand never stands down for a live one, an automatic attempt stands down for another replica's live attempt started by hand whenever either started (a worker that slept mid-job and wakes beside the phone's Run here yields after at most its call in flight), and of two live automatic attempts the earlier start goes on (`AttemptRecord.yields(to:)`). A resumed attempt keeps its start, so it outranks a later automatic attempt elsewhere, which stands down when it sees the resumed one live. The vault's worker is a `jobs_worker` record (`WorkerRecords.designate`, one per vault, its replica or none and since when, the later write winning), declared in `JobSchema.workerEntities` apart from `JobSchema.entities` so registries already frozen with the job kinds stay as they are; an app adds it with a new registry version.

Product cores are depended on the same way, through `ProductModule` (`.product(.novelForgeCore)`), so no dependency is named by a string.

### Sync runtime

`ShadowSyncRuntime` attaches a vault to a storage location, works out where it stands, syncs it on a schedule and reports a status; it has no UI.

- **Location.** `SyncLocation` names the provider (`SyncProviderSettings`: the non-secret settings of iCloud, a local folder with its bookmark, S3, OneDrive or Google Drive), the vault id and a `SyncAccountBinding` (a domain-separated SHA-256 of the account, never the account itself). `SyncLocationStore` keeps it as JSON at `<Application Support>/<bundle id>/Sync/location.json`, refuses a path inside a vault directory and writes atomically. `load()` answers `firstUse`, `turnedOff(reason)` or `attached`: `turnOff()` leaves a `location.json.off` mark beside the file (`disconnected`), a saved location wins over the mark, and a corrupt or oversized file (`unreadable`) or one of a newer format (`newerFormat`) also reads as turned off, so nothing attaches on its own once a location has existed. A refused file is `permissionDenied`; the start-up driver decides whether that is the device lock.
- **Locked device.** `FirstUnlockProbe` answers whether the device has been unlocked since it started, by reading or creating a file protected until first user authentication; `UIApplication.isProtectedDataAvailable` would stop background sync whenever a phone locks. The keychain's `errSecInteractionNotAllowed` is typed: `SecureStoreError.isInteractionNotAllowed`, `KeyRingError.deviceLocked`. So is `errSecMissingEntitlement` (-34018), which the data protection keychain answers to every add and delete of a build that carries no application identifier, such as one signed without a team, while its reads find nothing: `SecureStoreError.isMissingEntitlement`, `KeyRingError.keychainUnavailable`, `SyncCredentialError.keychainUnavailable`.
- **Secrets.** `SyncSecureStores.keychain(app:sharedAccessGroup:)` lays out four keychain services under the app's bundle id: `.sync` (ring keys, synced, shared group), `.sync.credentials` (S3 credentials through `S3CredentialStore`, synced, shared group), `.sync.device` (the device marker, this device only) and `.sync.tokens` (OAuth tokens through `KeychainOAuthTokenStore`, this device only, the app's own group). The stores and their errors never show a secret.
- **Setup.** `VaultSetup` discovers a vault by its hint, or by a manifest header when the hint is missing or unreadable; objects outside the vault layout (an S3 probe) do not count. `create()` joins a vault that is already there; otherwise it inserts a new ring key into the keychain first and only then puts `vault.json` if absent, so no device sees a vault whose creator holds no key. A lost race, or a read-back that shows another hint, joins the winner; the unused key stays (keychain items are write-once). `join(_:)` refuses a location whose hint names another vault. On a provider without atomic put-if-absent (Google Drive, S3 without conditional writes) two devices can still both win when each reads its own hint back before the other's overwrite lands; the loser's next evaluation then reports `vaultMismatch`, and what it uploaded under its own vault id stays unreadable to the others. Resetting a vault whose keys are lost everywhere is not here yet: it waits for the decision on deleting outside recorded names.
- **Start-up.** `SyncStartup` (an actor; calls run one at a time) returns a `SyncPhase`: a `VaultStartupState` or `deviceLocked`, `keychainUnavailable` (the keychain refuses this build), `accountUnavailable`, `accountChanged`, `storageRemoved`, `appUpdateRequired`, `detached`, `settingsUnreadable`, `vaultMismatch` or `vaultUnrecognized`. A disconnect reads as `detached`, an unreadable location file as `settingsUnreadable` and a newer one as `appUpdateRequired`. On first use it attaches the automatic provider (iCloud) on its own, creating a vault only when the provider answered that it holds none; every other provider, and turning sync back on, goes through `attach(_:choice:)` with an explicit create or join, and `detach()` turns sync off for good. iCloud, OneDrive and Google Drive attach only with an account binding. A saved location is never replaced: another account, another vault at the location or an empty location stops sync and touches nothing. Since a refused build reads every item as missing, which would look like a vault awaiting its key, every evaluation of a location (first use, after an attach, an attached vault) and every `attach` first adds and deletes a probe item in the this-device store, before any provider is made (S3 would read its credentials as missing and fail for the wrong reason); a success holds for the life of the `SyncStartup`. A refused probe is `keychainUnavailable` on evaluation, so an attached vault or one met on first use stops before anything is read or written at the location, and `SyncStartupError.keychainUnavailable` from an explicit create or join, which then saves no location. The ring keeps its own mapping, for a keychain that refuses reads of the shared access group. A device marker that is not a replica id is cleared once the device is unlocked, so the next start re-mints the replica. Vault phases come with a `SyncAttachment` that builds the `ReplicaLifecycle` and `SyncEngine`. `SyncPhase(failure:)` maps a sync call's failure to the phase it causes, and `noteMissingKeys(_:vault:)` feeds the keys a download of the attached vault found missing.
- **Runtime.** `SyncRuntime` (an actor, one per vault store) owns a `SyncStartup`, the `SyncEngine` of the attached vault and the schedule. The app calls `start()` once at launch, `foreground()` and `background()` from the scene phase, `localWrite()` after each committed write and `changeNotice()` for a silent push; `discover(_:)`, `attach(_:choice:)` and `detach()` serve the settings screens, and `shutdown()` ends it. Runs never overlap: attach, detach and discovery wait for the run in flight, and every trigger that arrives during a run joins one follow-up run. The triggered calls return once the runtime is idle, so `background()` can end an iOS background task. A run evaluates the phase when asked (launch, foreground, key check) or when none is known, starts the engine once per attachment (after `.lifecycle(.markerUnavailable)` it evaluates again, which tells a locked keychain from a corrupt marker), downloads, passes the outcome's `missingKeys` to `noteMissingKeys(_:vault:)`, runs the attachment's `RecoverySetup.reconcile()` after a download that applied files or brought a key into the ring (and again after the next download if it failed), uploads only while the store holds pending changes, and compacts and adopts at most hourly on a catch-up run. On `detached`, `accountChanged`, `storageRemoved`, `settingsUnreadable`, `vaultMismatch`, `vaultUnrecognized` or a lost CloudKit zone it drops the engine, stops uploading and returns the vault to device backups (`StorageAttachment.detach`; a store pinned out of backups is left as it is); a locked device, an unavailable account or an app update keeps the exclusion. It listens to the change notices of the attached engine's provider and, for iCloud, to its `CloudKitStorageProvider.conditionChanges()`; after any failure it reads that provider's `condition()`, so an account switch or a deleted zone stops sync even when the notice was missed. `SyncStartup` keeps the attached location's provider for as long as it stays attached, beside one for the latest discovery elsewhere, so looking at another location never makes a second provider for the attached one (two CloudKit providers of one container would share its index state). `shutdown()` lets a run in flight finish, and calls waiting on it return only after it.
- **Key services.** `SyncRuntime.keyServices()` returns a `SyncKeyAccess` for the attached vault in any vault phase, including `awaitingKey`, when no engine runs yet; it waits for the run in flight only while no evaluation has answered, and throws `notAttached` before the first evaluation or `unavailable(phase)` for a phase without an attachment. Every call of an access that reaches storage or the store first asks the runtime whether it still attaches the vault at the same location through the same provider; after a disconnect, a move or an account change it throws `unavailable(phase)` (`RecoveryError`, `KeyExchangeError`) and touches nothing, so a screen held open never reaches another account's storage, and the same access works again if the original account returns. `holdsKey` reads the ring, so it turns true as soon as a recovery or an exchange adds a key. The recovery phrase goes through the access too: `recoveryStatus()`, `beginRecoveryPhrase()` and `commitRecoveryPhrase(_:confirming:)` use the attachment's one `RecoverySetup`, shared with the engine's reconciliation, and a commit throws `noRingKey` while the ring is empty. `recover(with:)` runs `PhraseRecovery`; `requestKeys()` returns a `SyncKeyRequest` for the requesting side of the QR exchange (`payload`, `receive`, `accept(confirmingCode:)`, `cancel`); `respond(to:)` answers a scanned request and passes the vault's `ReplicaDirectory.keyFloor` to `KeyExchangeCoordinator.respond(floor:)` itself (a directory that cannot be read sends the oldest keys first). Once a recovery or an accepted exchange leaves a key in the ring, the runtime evaluates again without waiting for the 30-second key check, joining a run in flight as one follow-up, so the phase leaves `awaitingKey` and the first sync starts; the calls return when the keys are in the ring, not when that run ends, and `statusUpdates()` reports the outcome. `RecoveryStatus.standing(ofRecipient:)`, given the `recipientID` of the phrase the user wrote down, says `notSetUp`, `active(createdMillis:)` or `replaced(byRecipientID:)`: another device recorded a newer phrase, so the one the user holds no longer recovers new keys. The app has to keep that recipient id itself, as it keeps the fact that the user confirmed the phrase. `keyHolders()` lists every key of this device's ring with the replicas that have shown they hold it: each replica's newest file at the location (its manifest, else its newest segment, else its newest base part, up to 16 MiB, for the 64 newest replicas) must open under that key, header and every chunk authenticated against its path, and replicas the directory records as retired are left out. A readable manifest names the key the replica writes with now, so one under a key this device lacks rules the replica out; only an absent or unreadable manifest falls through to older files. A replica writes with one key at a time, so it shows under that key only, and nothing is said about keys this device does not hold or about any keychain's sync state.
- **Blobs.** Binary attachments (receipt images, exports) sync beside the change log. `VaultBlobs(store:)` puts one (`put(_:)`, or `put(contentsOf:)`, which copies and hashes a file a chunk at a time) into `<database>-blobs/` beside the database, so the directory's backup policy and file protection cover it (an in-memory store keeps none: `noDirectory`), records it in the kernel table `sync_blob` and returns a random `BlobID` (64 hex digits); nothing in an id or an object name derives from the content. The contract: a blob is named only by its `BlobID.description`, verbatim, in a synced field of the same store that put it, and within `blobRetention` of the put. Local tables (`nf_local_*`, `mm_local_*`), derived tables and other stores are not read, so an id kept only there, or written into another store, does not keep the blob. A blob carries the most restricted sync class its store's registry declares, and anything over `SyncConfiguration.maximumBlobBytes` (64 MiB) is refused as `tooLarge`. Every upload puts the waiting blobs before its segments, so a provider failure keeps both back and the runtime's backoff retries them (a blob whose local file cannot be read is logged and left waiting while the segments go up); the table survives a relaunch, and the runtime uploads while a blob waits even with no pending change. A blob of a class the provider refuses stops the upload before anything is put (`SyncError.blob(.classRefused)`), as a refused change does. In storage a blob is `blobs/<id>/<part>-of-<parts>`: each part is a vault file in the segment format (stored codec, a canonical header line of kind `com.shadow.library.shadowsync.blob` naming the blob, its class, size, SHA-256 and the part's offset, then the bytes) of at most `blobPartBytes` (8 MiB) and the provider's object limit, sealed and opened a chunk at a time. `SyncRuntime.fetchBlob(_:)` returns the local file, or fetches a complete part set, verifies every chunk, the part headers and the digest into a temporary file and keeps it (`missing`, `corrupt`, `keyUnavailable`, `classRefused`, `notAttached`). Compaction removes only blobs this database put, by the part names it recorded: once nothing in the merged vault state (the own writes are not consulted) or the unsent changes has named one for `blobRetention` (30 days), every active replica has published a manifest whose applied points reach how far each stream was applied when the blob was first found unnamed (this database's own stream up to the last change it logged, sent or not, and retired streams too), and this database has applied each such replica up to its manifest's head. A release starts again when a stream it names retires or is no longer applied here, and at every re-mint. A manifest now states the applied points of the last moment its change log held no unsent change, so a change written before the drop was seen is never missed. A removed blob keeps its local file for another `blobRetention`, and compaction lists `blobs/` once to put back any named blob that storage lacks and this device holds; an unsent change naming a blob held here but not put by this database puts it again first when storage lists no complete copy of it. Removed records (a removal flag) keep their blobs; purges and overwritten registers release them. Every provider must pass the blob cases of `StorageProviderConformance`, including one listing of `blobs/` across pages. Removal waits for every active replica's manifest: a replica that is never retired but never syncs again stops it, and on a local folder (no server time) a manifest is written only when its replica completes a base or deletes files, so removal there can wait until every other replica next does, which can be weeks.
- **Routes.** A `SyncStoreRoute` (`stores/<name>/`, a name of up to 32 lower-case letters, digits and hyphens) syncs a further store of the vault at the primary's location as a vault of its own, whose id is derived from the primary's (`com.shadow.library.shadowsyncruntime.store-route`) and whose files are sealed with the primary's keys, so one ring, recovery phrase and key exchange cover every store; the name is part of the stored layout. `SyncStartupEnvironment.route` makes a route runtime: it never attaches on first use, throws `notAttached` from `attach`, `detach` and moves, and syncs through `RoutedStorageProvider`, which prefixes every key; the primary's listings never reach under `stores/`. A primary whose environment lists `routedStores` refuses `moveVault` and `followMove` with `routedStoresUnsupported`, since a move carries only the primary's store. `SyncRuntime.attachedLocation` gives the attached location and its storage's class policy in any vault phase.
- **Schedule.** `SyncScheduler` runs on offsets of the injected `Clock` (`ContinuousClock` by default, never the wall clock), with the intervals of `SyncSchedulePolicy`: sync on launch and foreground, upload 2 s after the last local write, download every 45 s while in front (counted from the last download, so steady writes never postpone it), look for the vault's key every 30 s while waiting for it, and upload once on going to the background, dropping a backoff the device chose so the final upload is never skipped. In the background nothing is timed: a write there, a notice or a push runs at once. A storage `rateLimited(retryAfter:)` holds every trigger, foreground included, until it passes (at most an hour); other transient failures back off from 2 s doubling up to 5 minutes, which a foreground skips.
- **Status.** `statusUpdates()` yields the current `SyncStatus` and then each change in order: `off` (no sync set up, or the user turned it off), `upToDate`, `syncing` (a launch or foreground catch-up, local writes not yet uploaded, or a retry pending; quiet polls do not show it) or `attentionNeeded(SyncAttentionReason)`. Each reason says what it stops through `stops` (`everything`, `uploads`, `downloads(from:)` the named replicas, `nothing`): `quotaFull`, `accountUnavailable`, `accountChanged`, `storageRemoved`, `zoneLost`, `vaultMismatch`, `vaultUnrecognized`, `awaitingKey`, `writingKeyMissing`, `keysMissing(replicas:)` (the replicas whose files are sealed with keys this device lacks), `wrongClock` (uploads stop only while the store stamps with the wrong clock), `appUpdateRequired`, `deviceLocked`, `keychainUnavailable` (the keychain refuses this build; nothing retries it on a timer, and each foreground evaluates again, which costs one refused keychain add), `settingsUnreadable`, `storageUnreachable` (after three failed attempts in a row) and `failed(code:)`. When several apply, the one that stops the most is shown. The library holds no user-facing text; the app words each reason.

### App shell

`ShadowAppShell` is the SwiftUI app code that is not about one product: an app links it, passes its `AppIdentity` and supplies what only it knows. Like `ShadowDesignSystem` it defaults to `MainActor` isolation.

- **Identity.** `AppIdentity(id:displayName:vaultNoun:vaultTitle:exampleBucketName:)`: the app's `com.shadow.apps.<app>` id names its keychain services and defaults keys (`<id>.ai` for provider keys, `<id>.ai.settings.v1` for AI settings, `<id>.sync.recovery-recipient.<vault id>` and `<id>.sync.recovery-offer-declined.<vault id>`, and `SyncSecureStores.keychain(app: id)`); the display name and the vault noun ("library", "Library") fill the screens' sentences, and the example bucket name ("my-novels") is the S3 form's placeholder. Each public shell view puts the identity in its environment for the views inside it; a view shown without it fails an assertion in debug builds. Novel Forge passes `.novelForge`, whose names are those its installs already hold. The shell names no app itself; its loggers use `Logger(category:)`, so their subsystem is the app's bundle id.
- **Vault.** `VaultModel<Opened>` opens what the app opens from its vault (Novel Forge one `VaultStore`, through `NovelForgeVault`) with the app's opener off the main actor, waits as `locked` before the first unlock and joins an open in flight. `VaultDirectory.default()` is `<Application Support>/<bundle id>/Vaults/Default/`, beside sync's own files (`SyncPaths`).
- **Sync.** `SyncRuntimes.live(identity:)` with its wiring, the status indicator (`SyncStatusIndicator`), Sync Settings (`SyncSettingsView`), Keys and Devices, and `SettingsTabs`, whose tabs an app extends with its own `SettingsTabs.Tab` values. An app launches a `SyncedVault`: its primary `VaultStore`, which attaches, detaches, moves and serves the key screens, the routes it declares and a closure that names the `SyncedStore`s to route for the attached storage's class policy. `SyncRuntimes` runs one `SyncRuntime` for the primary and one per route it names: routes start once the primary has an attached location, are asked again on every primary status change and on `reroute()`, start without waiting for their first run, stop when no longer named (sending stops at once through `SyncRuntime.stop()`, at most the put in flight lands, the records stay, and no new runtime takes the store before the old run ends), and look for a key at once when the primary's arrives. `status` is the worst of them (attention before syncing before up to date; among attentions, what stops the most; the primary on a tie), and `attentionScope` names a route's data when its problem is shown. A vault that declares routes cannot move yet: `canMoveVault` is false, Sync Settings shows why instead of the move button, and the primary's runtime throws `SyncMoveError.routedStoresUnsupported`. An app adds its own section to Sync Settings with `syncSettingsSection { … }`.
- **AI.** `AIServices.live(identity:disclosures:requestGuard:defaults:)`: the app supplies its `ConsentDisclosure`s (id, data class, title and explanation) and the screens every route gets, with no default (Novel Forge passes its hard-line screens); the OpenRouter application title is the display name. `AISettingsButton(store:links:)` takes the links its iPhone and iPad sheet adds beside Sync.
- **Errors and reads.** `PresentedError(_:)` gives a store failure the store's words and a core's `DomainFailure` (`ShadowStore`; Novel Forge's `DomainError` adopts it in its core) its code, or the words of the store failure it wraps; an app adds its own words for known codes (Novel Forge's `PresentedError(_:known:)`). `ReadObserver`, `Loadable`, `UnsavedWork` with `flushingUnsavedWork()`, `fillingSurface()` and `CostSettler` are shared as they were.
- **Strings.** The screens' strings live in the module's own catalogs (`Resources/`: `Sync`, `SyncSettings`, `SyncKeys`, `AISettings`, `AppShell`) and are looked up with `bundle: .module`; SwiftPM builds them into the module's bundle and Tuist into `ShadowKit_ShadowAppShell.bundle` inside the app. Keys carry the app's words as `%@`. The entries have no `extractionState`, so SwiftPM generates no symbols for them (keys such as "Recovery phrase" and "Recovery Phrase" would collide).
- **Stays in the app.** What names a product's core: Novel Forge's `VaultOpener`, `JobRuntimes`, `JobRunHosts`, `ContinuedProcessingHost`, worker mode, the Settings scene with its Devices and Worker tab, and the sentence embeddings (`AIServices.embedders`).

1. Add a target and a `.library` product to `Packages/ShadowKit/Package.swift`, with sources in `Sources/<Module>` and tests in `Tests/<Module>Tests`.
2. Add a case to `SharedModule` in `Tuist/ProjectDescriptionHelpers/SharedModule.swift`.

## Memoir core

`Packages/MemoirKit` holds `MemoirCore` (bundle id `com.shadow.library.memoircore`), Memoir's records, rules and derived state; it imports no UI framework and depends on `ShadowCore`, `ShadowStore`, `ShadowSync`, `ShadowText`, `ShadowAI`, `ShadowJobs` and GRDB. `LocalDate` (`Calendar/`) is a civil date held as days since 1970-01-01 (years 0000 to 9999), computed with integer arithmetic only, never `Calendar` or `TimeZone`; it parses and formats `yyyy-MM-dd` and encodes as that string. Its fixtures follow `Packages/MemoirKit/Fixtures/README.md`.

### Memoir calendar

`Calendar/` ports the reference's calendar (`rules/time.ts`, `rules/recurrence.ts` and `finance/subscription-cycle.ts`). The civil-date arithmetic (month arithmetic clamped to the month's end, Monday-anchored weeks, nth weekdays) runs on `LocalDate` in integers, with no `Calendar` or `TimeZone`. `RecurrenceRule` expands daily, weekly, monthly and yearly rules as the reference does: an excepted date keeps its index and so uses up a COUNT slot, and an expansion returns a cursor from which the next window resumes with the same occurrences and indices as a full recomputation. `SubscriptionCycle.advanceDueDate` rebuilds each month-based due date from the billing day. `IssueClock` is the only code that reads Foundation's `TimeZone`, and it runs only while this device issues a command: it gives the UTC offset in force and the local date (`stamp(at:)`), resolves a local minute with the reference's rules (in a fold the earlier instant, in a spring-forward gap the transition), measures local days, and clamps a claimed `performedAt`. Replay never calls it and uses the offsets and dates the commands recorded, so two devices with different tz data agree. The vectors in `Fixtures/calendar/` pass exactly. The zone cases cover 20 zones from 2015 to 2030, and every disagreement between Foundation and ICU sits in `zone-exclusions.json` with its reason (none so far). The native code deliberately differs from the reference in these cases:

- It counts years 0 to 99 as real years, where the reference's `Date.UTC` reads them as 1900 to 1999.
- `RecurrenceRule.init` throws `noWeekdays` for a weekly rule without weekdays and `dayOfMonthOutOfRange` for a monthly day of month below 1. The reference's payload parser (`quest-command.types.ts`) accepts any integer and then produces dates that do not exist.
- `IssueClock.resolve` throws `minuteOfDayOutOfRange` for a minute outside 0 to 1439, where the reference rolls into the neighbouring day.
- `SubscriptionCycle.init` throws `billingDayOutOfRange` outside 1 to 31. The reference relies on its database check, and its function only clamps a day of 32 or more to the month's end.
- `utcOffsetMinutes` and `stamp(at:)` floor an offset with seconds (local mean time, before 1972) to whole minutes, where the reference returns a fraction. `stamp(at:)` takes `issuedOn` from that recorded minute offset, as `MemoirCommand` checks it.
- Expansion and arithmetic stop at 9999-12-31; the reference has no upper bound.

`Commands/` refuses these inputs before they become commands (the billing day through `SubscriptionRecord`'s `CommandContent` check), so that every device replays only what the native calendar accepts.

### Memoir rules

`Rules/` ports the reference rules engine (`src/modules/rules`, without the calendar functions): `Ruleset` and the frozen `Ruleset.v1`, the level curve, reward, timing bands, streaks and shields, HP, Crown, Comeback, Returner, momentum, capacity, achievements and titles. Arithmetic is exact and integer only, with no `Double` or `Float`: modifiers and ratios are `Thousandths`, momentum weights `Tenths`, Crown weights and medians `Halves`, derived values an exact `Fraction` compared by cross-multiplication, and wherever the reference calls `Math.round` the port rounds halves toward positive infinity as it does. Products and sums go through `Int128` and saturate at the edge of `Int` instead of trapping. The level table (`LevelCurve+V1.swift`) is generated from the reference's curve and never edited. A published ruleset never changes: `Fixtures/rules/ruleset-v1.json` pins `Ruleset.v1` by the SHA-256 of its canonical JSON, and a change means a new version. Every vector in `Fixtures/rules/` passes exactly except the 2,593 cases in `divergences.json`, where the reference's float result differs from an exact rational model of the same rule; for those the tests assert that the native result equals the exact model and differs from the reference. Only two of them change an outcome (momentum at exactly the cold ratio, which the reference's float reads as `cold` and the port as `steady`); the rest are fractional fields such as the reward modifier, the momentum ratio and the capacity baseline.

### Memoir schema

A vault is three stores in sibling directories, each opened only through `MemoirStore.open(_:in:wallClock:)` (or `openInMemory`) with its own registry from `MemoirSchema`: the main store `Vaults/<name>/vault.sqlite` holds the general-class kinds and admits only `.general`; the activity store `Vaults/<name>-activity/activity.sqlite` holds activity-class metrics so the iCloud setting for Activity can switch on and off without moving records; the restricted store `Vaults/<name>-health/health.sqlite` holds health-class kinds (weights, health metrics and their days). The activity and restricted stores are always excluded from device backups. Kinds are prefixed `mm_`. Everything that moves hero state is an appended `mm_command` (UUIDv7 id, type, payload, instant, UTC offset, issued-on date, optional occurrence, ruleset version) whose payload never carries the owner's words, a measured value, or a threshold of an activity- or health-class metric: those live in records of the metric's class (or content records such as `mm_quest`, `mm_journal_entry`, `mm_command_note`) that the command names by id or date. `CommandPayload` enforces what it can: strings are tokens and never digit-only, integers appear only at the paths `CommandPayload.integerPaths(for:)` pins for the command's type (schedule minutes, counts, calendar positions), and keys naming a measurement (`kg`, `value`, `healthThreshold`, ...) are refused. Quest deletion and subscription cycle confirmation are commands; a subscription record keeps only the owner's anchor date. `mm_fx_rate` (first writer wins), `mm_expense_category`, `mm_account_settings`, `mm_weight` and `mm_metric_day_{general,activity,health}` are natural-key records. Data is written through the typed records in `MemoirCore/Records` (`create`, `edit`, `remove`, `restore`, `append`; `restore` only clears the removal), never by setting raw fields; an edit writes only what changed and cannot alter a first-writer field once set. Each registry is frozen in `Packages/MemoirKit/Fixtures/schema/` (`registry-v1.json`, `activity-registry-v1.json`, `restricted-registry-v1.json`); adding kinds or fields raises that store's version in `MemoirSchema` and saves the new description beside v1.

### Memoir commands

`Commands/` is the command vocabulary: `MemoirCommandKind` names the 40 types (the reference's 36 handlers, the time-zone, intensity and returner-threshold settings, and `receipt.scan`) and `MemoirCommandBody` has one typed case per type, decoded from a payload with the reference's checks and field names (`quest-command.types.ts` and each handler's `require*` helpers) and encoded back. A command is built only from a body (`MemoirCommand(id:body:...)`), and a stored command of a known type whose payload does not decode as its body reads as unreadable; one of an unknown, newer type is held to the payload's own rules. A payload keeps the reference's key names for what stays in it and carries only ids, dates, closed-set tokens, flags and the integers its type pins (`quest.create`'s schedule and recurrence positions, `quest.update`'s under `patch.`, `quest.reschedule`'s `toMin`, the returner threshold); the owner's words and values are the records the command names (a weight by its date in the restricted store, a metric's day by metric and date, a quest, entry, expense or subscription by id), and a reason note or reflection is the command's `CommandNoteRecord`, which the payload marks with `note: true` or `reflectionText: true`. The occurrence is the command's own field, never the payload's. Beyond the reference, decoding refuses any key the type does not have (so adding a field to a type's payload needs a new ruleset version, or older devices read the command as unreadable), a non-boolean flag the reference reads as false, a quick-log or billing date that is not a real date, a monthly day below 1, a health threshold on a quest (it needs a record kind first), a log edit that sets both texts, a category other than the reference's nine built-ins (`FIN_005`), and a time zone that is not `UTC`, `GMT` or an `Area/Location` name. Rules that need state (whether the occurrence exists or has begun, the edit window, the reschedule cap, coins, earned titles and owned cosmetics, `QST_003` against the quest's current start time) are replay's. `CommandIssuer` stamps a body with a UUIDv7 id, the instant, the offset in force and `issuedOn` from `IssueClock.stamp`, and `Ruleset.current`'s version, and appends it with its note in the caller's transaction; `issue(_:text:content:in:)` first runs the reference's checks on the record the command names (`CommandContent`: names, mood, calories, weight, and the subscription's `BillingTerms`), which the caller still writes through its typed record, and `confirmCycle(_:in:)` writes the cycle's expense through `SubscriptionCycles.confirm`, logged at the command's instant, and appends the command in the same write. A reason note is 1 to 120 UTF-16 units (`CommandIssuer.validate(text:for:)`). `issuedOn` is the zone's date, never the account's open day: after a backward zone change the open day runs ahead of it (`rules/time.ts:157-161`), and since the open day is derived state, replay takes the later of the two. Settings carry `SettingTiming`: a time zone or intensity change is `staged`, as the reference stages it, and takes effect on the day the replay's day walk next prepares, after every elapsed day has closed under the setting it was lived under (`rollover.service.ts:369,427-436`), so the days an absence leaves close under the old setting; a later staged change replaces one still waiting. The returner threshold, and the first time zone, which the reference's onboarding sets outright, apply at once. A time zone is checked against this device's zone data, under exactly its name, when issued, and only for its shape when decoded, so a device with older data replays it alike. The vectors in `Fixtures/commands/` pass, and each case where the native code differs from the reference carries its reason.

### Memoir replay

Hero state is derived, never synced: `Replay` (`Replay/Apply`) orders the `mm_command` items by the kernel's clock on the appended item, then by id (`Replay.commands(in:)`, `Replay.ordered`), and folds them into a `ReplayState` (`Replay/State`) with `Replay.run`, or one at a time with `Replay.step`, so the same commands always give the same state on every device. Each command runs under its own `Ruleset.version(_:)` and reads only what it recorded (instant, offset, `issuedOn`), never the device's clock or zone data; the account's day is `max(issuedOn, open day)` (`rules/time.ts:157-161`), and an occurrence counts as begun up to five minutes before its day at the recorded offset. `recovery.complete` and `plan.setLock` act on the open day alone: one issued on a day the open day has already passed is refused (`CMD_002`, as the reference's `requireToday`), unless a time-zone change that took effect after the issuing day and no later than the open day explains a gap of at most two days. A handler ports the reference's (`quest-commands`, `compassion-commands`, `progression-commands`, `quick-logs-commands`, the metric and finance handlers), with its refusals as `ReplayRefusal` named by the reference's code (`QST_001` to `QST_009`, `CMD_002`, `RCV_001`, `LCK_001`/`002`, `HRO_001`, `CSM_003`, `TTL_001`, `MET_002`/`003`, `FIN_003`/`004`, `QLG_001`) and its `rejected` answers (the reschedule cap, an unconfirmed weight replacement) as `ReplayRejection`; every handler refuses before it changes anything, so a refused command is recorded in `outcomes` and changes nothing else, and replay mutates one state in place, reading a day or a window of days through date-indexed tables (`OccurrenceTable`) rather than the whole history. The first terminal action for a quest and date in replay order wins and a later one is `superseded`, except that a user's outcome replaces a system miss or bare reschedule marker; a purchase the merged balance no longer covers is refused and withdrawn with a `ReplayNotice`. A command this app cannot read (unreadable item, unknown type, unknown ruleset version) sets `halt` and replay stops there. The state holds quests with their schedules (names stay in `QuestRecord`), logs per occurrence with the quest snapshot the reference logs, reschedules, streaks and shield uses, the hero ledger (`HeroLedger`: XP, level, coins, stats and the dedupe-keyed event trail), achievements, titles and cosmetics, each day's plan lock, Comeback and Crown (`ReplayDay`), Recovery quests and the Returner (`CompassionState`), the settings with the day each takes effect (`ReplaySettings`), and what earlier commands named (`RecordIndex`: a deleted metric stays known, inactive, as the reference's soft delete; a confirmed cycle's expense id is known, so its edits apply), so replay is a function of the command log alone and a device without the health- or activity-class records replays the same. A built-in metric (`BuiltinMetric`) exists on every device, so its update or deletion is refused (`MET_003`) and its registration accepted. `Fixtures/replay/` runs the reference handlers and its rollover walk over the same steps; deliberate differences: `FIN_006` is enforced by `ExpenseRecord`'s first-writer currency rather than by replay, and `MET_004` never arises, since no quest declares a metric consequence natively.

The day walk (`Replay/Days`) is the reference's rollover gate, run before every command: `Replay.step` closes every day before the command's `issuedOn`, opens that day, then runs the handler (the internal `Replay.apply` runs the handler alone, for vectors that set up the days themselves). Closing a day (`closeDay`) writes a miss for each scheduled occurrence nobody resolved, which a later user outcome still replaces, breaks streaks or uses shields, expires the pending Recovery quests dated up to it, charges HP once per quest and date, settles the Crown (the endowment on a period's first day, a forfeit per break, the bank on its closing day), counts full-HP and cleared locked days and dates the last activity. Opening one (`prepareToday`) reads momentum, fires the Returner, arms Comeback, spawns a Recovery quest for yesterday's anchor or routine misses, expiring at the next midnight of the offset the walk recorded, and sets the day's HP and Crown. A day is judged under the settings in force on it, a staged change being promoted on the day the walk opens, and the highest ruleset version replay has seen, the command's own included; a command that halts replay moves no day. While a zone change is staged, the day is still measured in the zone it replaces, from the offset the change was issued under, never zone data: the walk closes the days before the replaced zone's date at the driving instant, promotes the change and opens the later of that date and the driver's own. After a forward change the dates between are never lived and never closed, and after a backward change the opened day stays open until the new zone's date passes it (`rollover.service.ts:437-447`). For this, the app stamps a command, and its horizon, with the zone in force, and once the zone in force has passed the open day, with the staged zone that the walk will then promote; a device still stamping the old zone lives the first day of a forward change instead of skipping it. The walk never closes a day more than 90 days before the replaced zone's date (`ReplayState.catchUpLimitDays`, `rollover.service.ts:155,177`), so an old open day stays open. `Replay.run(_:through:)` replays the whole log and takes a horizon, the app's local day as an `IssueStamp`, closing the days before it without commands; the horizon only walks forward and comes after every command, so the state without it is the one later commands extend (`Replay.extend(_:with:through:)`, which throws `ReplayOrderError.outOfOrder` for a command that sorts before the state). Commands are taken strictly in clock order: `Replay.step` ignores a command already taken in, answers `outOfOrder`, changing nothing, for a new one that sorts before the latest one taken, and a replay from an earlier state (a checkpoint, see below) recomputes every day after its place, so a completion made on time on a device that synced late counts on time, where the reference never reopens a closed day. A command issued after its occurrence's day closed is the reference's offline completion: its outcome replaces the miss and the closed day keeps its HP and Crown.

### Memoir projection

`MemoirReconciler` (`Projection/`) is the main store's `StoreReconciler`, passed as `MemoirStore.open(.main, ..., projection:)` (the other stores refuse it). It keeps the `mm_derived_*` tables (`mm_derived_hero` with the totals, the zone in force, the staged one and the latest recorded offset, the staged intensity, the returner threshold, lifetime counts and, when replay halted, `needsAppUpdate` and the halt; `mm_derived_quest` with each quest's schedule and streak; `mm_derived_quest_log` per occurrence, with whether a shield bridged it; `mm_derived_reschedule` per rescheduled occurrence; `mm_derived_day` with HP, Crown (granted and remaining), the lock and the quests it names, Comeback, Returner and Recovery; `mm_derived_recovery` and `mm_derived_returner`; `mm_derived_hero_event`, the latest 32 listed entries of the hero trail (a Crown period opening is never listed); `mm_derived_unlock` for achievements, titles and cosmetics; `mm_derived_notice`; `mm_derived_quick_log` with whether each journal entry, meal and side quest earned its reward, by record id, as replay last decided it (a weight records none); `mm_derived_quick_log_day` with the rewards each of those kinds earned per day summed from the hero trail, so a side quest whose id two commands named counts every slot it took) equal to `Replay.run` of the whole log through the app's horizon, read with `MemoirDerived`. It does not replay the log on every merge: `mm_local_replay_command` holds each command's clock, so a merged, re-delivered or purged command gives the earliest place that changed; checkpoints at or after it are deleted, replay resumes from the latest one strictly before it (`mm_local_replay_checkpoint`, `ReplayCheckpoint`) with `Replay.extend`'s rules, and a new checkpoint is saved wherever a command's walk is about to close a day: the state of every command up to the one before, with its position, day, ruleset version, the projection's fingerprint and a SHA-256 digest over all of them (domain `com.shadow.library.memoircore.replay-checkpoint`). The last `MemoirReconciler.recentCheckpoints` (7) and the last of every month are kept. The horizon (`IssueStamp` from the app's closure) walks a copy for the view only, so a checkpoint never holds a day the horizon alone closed; `refresh(_:)` rewrites the view at launch and when the local day changes. `ReplayState` and its parts are `Codable` (`ReplayState.codingVersion`; schedules in `quest.create`'s payload shape; recurrence cursors are a cache and never saved) with a canonical encoding, `canonicalJSON()`, in which equal states give equal bytes, and decoding refuses a state whose parts contradict each other (a hero whose totals are not the trail's sums, rows filed under another id or date). A checkpoint written by another fingerprint (layout, schema registry, ruleset, `replayVersion` or the app version the app passes), for a ruleset this build lacks, or that fails its digest or its row is deleted and replay falls back to an earlier one or the start; a changed fingerprint drops every local and derived table and rebuilds, as does clearing the vault scope. All of it runs inside the merge's write transaction, so an interrupted reconcile leaves nothing half-written; the in-memory cache of decoded checkpoints is keyed by digest.

### Memoir finance

`Finance/` holds money in Int64 minor units with checked arithmetic and an ISO 4217 exponent table (`ISO4217`). `HomeConversion` converts with the exponents applied, `roundHalfUp(amountMinor × rate × 10^(eHome − eSource))`, exactly from the rate's decimal text (`ExchangeRate`, at most 18 digits and 18 places), halves toward positive infinity as the reference's `Math.round`; the reference multiplies minor units by the rate without the exponents. Every case where it differs from the exact model (mixed exponents, binary-float rounding, amounts past 2^53 or past Int64), the custom intervals of zero or less the native code refuses, and the latest confirmed cycle winning in any order are listed in `Fixtures/finance/divergences.json` and asserted. An expense captures the `mm_fx_rate` of its own date when written (`createCapturingRate`); `RateFiller` fills the rest through a `RatesClient` that receives only currency pairs and a date (no network client yet: the service needs approval), rounds rates to eight places as the reference stores them, and records each pair and day once, first writer wins. `HomeConverter` converts every expense through that record, so devices agree even when an expense locked a rate that lost the merge. A subscription's next due and last confirmed dates are derived (`SubscriptionSchedule`) from its anchor date and its `subscription.confirmCycle` commands; an anchor moved to or before the latest confirmed billing date is ignored. Each confirmed cycle writes one expense under `derivedID("com.shadow.library.memoircore.subscription-cycle-expense", "<subscription>|<date>")`: a device that holds it never writes it again, but a device that has not received it writes it again, which with a later clock restores an expense the owner deleted elsewhere and reverts edits made elsewhere. `BudgetStanding` measures this month's spending in the home currency and counts expenses still waiting for a rate apart; changing the default currency clears the budget, and a budget in another currency is ignored. An expense deleted through `ExpenseEdits.delete` is marked removed, not deleted outright as the reference does: its note and merchant are cleared and its change records purged in the same write, and the entity is kept so its id can be created again. Created again, it keeps the currency, rate and logging time of its first write (first writer wins), and creating it in another currency is refused (`expenseFieldFixed`), where the reference inserts a fresh row with any currency.

### Memoir reads

`Reads/Quests` and `Reads/Hero` are the screens' read models, each a `ReplayReadModel` loaded with `VaultStore.load(_:_:)` or observed with `VaultStore.observe(_:_:)` (an `AsyncThrowingStream` over `observeReads`): `TodayBoard` (a day's occurrences with their state, the actions replay would take and the typed reason for each it would not, break costs, the Recovery quest, the day's HP, Crown, momentum, Comeback and lock), `QuestList`, `QuestDetail`, `StreakBoard`, `PlanBoard` (a week or a month grid), `DraftPreview` (a quest's effect on the coming week, computed without writing), `HeroDeck` and `ComingBack`. They read only the derived rows through `MemoirDerived` and the main store's records, never replay and never another store, so no health- or activity-class value reaches them; the words and catalogue names are the app's strings. An occurrence's actions are what replay would take, in the order its handlers check, with two client rules on top: a closed day keeps only the log's edits (`dayPassed`, as `quest-presenters.ts:73`; replay would still take a late completion there), and attaching a reason is `availableUntil` the log's seven-day edit window; `ReadAgreementPropertyTests` checks on random histories that what a board offers replay applies and what it blocks replay does not. Every model is as of the view's open day and says the next day it turns (`changesOn`). `AccountZone` (on the hero row) gives the clock in force and its `Source`: the account's zone on its open day, the staged zone once that day has passed as the replaced zone measures it, and the device's zone before any zone is set. A zone this device's zone data lacks is reported as `unknownZone` and keeps a fixed offset (the one the latest command recorded for the zone in force, or the one a staged change was issued under), falling back to the device's zone only when no offset was recorded. The app builds the projection with `MemoirReconciler(appVersion:now:deviceZone:)`, whose horizon is `now` in that clock, stamps commands with `CommandIssuer(clock: AccountZone.load(...).clock(at: now, device: .current))` read inside each command's main-store write (`QuickLogWriter` and `MetricCatalog` take a `CommandIssuerSource`, which resolves the issuer from the main store as each command is written, so a writer kept on a screen never stamps a stale zone), and runs `ProjectionDayTurns(store:reconciler:deviceZone:).run()`, which refreshes as it starts and then at each midnight of the clock in force, reading the zone again after every refresh; the app restarts it when the system clock or the device's zone changes significantly. Reading the derived rows was chosen over reading the checkpointed `ReplayState`: for thirty quests over two years the Today board reads in about 20 ms in a debug build, where decoding the latest checkpoint alone takes about 330 ms before it is extended and walked to the day. The web presenters they port (`fixture-provider.ts`, `quest-presenters.ts`, `hero-standing.service.ts`, `synced-hero-provider.ts`) are cited by line in the tests.

`Reads/Money`, `Reads/Logs` and `Reads/Reflect` hold the read models the Money, Log and Reflect screens show, as typed data and reasons, never copy. Each has an async read and an `observe…` stream that `ReadObservation` builds from `VaultStore.observeReads` on every store the model reads, health and activity ones included where the caller names their class, emitting again only when the model changes. `Reads/Money` (`MoneyReads`) computes from one `MoneyBook` read of the main store: the week, month and year spending with the delta against the same stretch before (`FinanceRange`, `SpendDelta`), the average per logged day, the category breakdown and per-currency totals, `BudgetStanding`, subscriptions with their due state, reminder day, monthly cost, upcoming charges and collisions, the expense listing (date range, search on note and merchant, category, newest first, paged with `PageRequest`), categories with their archived state, and an expense's history. Every home-currency sum leaves out the expenses still waiting for a rate and counts them in `PendingConversions` (decision 7). `AmountInput` reads what the owner typed into minor units exactly, with the separators of the owner's locale and the currency's ISO 4217 exponent, and refuses with an `AmountInputRefusal` what memoir-web would guess (a grouping that does not fall every two or three digits, digits past the exponent that are not zeros, a sign, any other character); formatting stays in the app. An expense is written through `ExpenseEdits` (`create`, `update`, `delete`) with its command; deleting one purges its `ReceiptRecord` (a removal would keep the field naming the image), so nothing names the image's blob and the sync kernel releases it. An expense created again after its deletion comes back without that receipt. Its history comes from the `expense.*`, `subscription.confirmCycle` and `receipt.scan` commands that name it, starting again at its latest creation. An edit also appends an `ExpenseChangeRecord` (`mm_expense_change`, main registry v4) under the command's id with the fields it moved, so the history shows typed diffs on every device. An edit that moves the currency, rate, receipt or logging time is refused (`expenseFieldFixed`, the reference's `FIN_006`). Creating or deleting an expense purges its change records, which hold its old notes and merchants, as the reference removes its audit rows; after a deletion the history lists the commands without their diffs. `Reads/Logs` (`LogReads`) reads the journal (word count and excerpt through `JournalText` on `ShadowText`), meals, side quests with the three-a-day reward cap, the entry-cap advisory (100 a month, from 80%), weight from the restricted store only (with `WeightConversion` through the exact international pound, rounded half up) and metrics from the store of each class asked for, with `ThresholdOffers`. `Reads/Reflect` (`ReflectReads`) builds the history stream (its search matches quest names, merchants, category labels, meal, side-quest and metric names; unlike memoir-web it never matches the kind, outcome or unlock labels, which are the app's copy), the insight statistics for 30, 90 and 365 days (a partial holds half an occurrence, a moved one counts where it moved) and the weekly review from `MemoirDerived`'s rows and the records; weight and metrics are read only for the classes the caller names. The review's answers and completion are this device's own, in `mm_local_review_answer` and `mm_local_review_completion` (`WeeklyReviewAnswers`), which hold only the week under review. Side-quest rewards, the day's reward slots and their XP come from the projection's quick-log tables, so they are what replay decided, never re-derived from the commands. A value past 30 significant digits or 18 places, or arithmetic past `Int128`, is left out of an average or conversion, never trapped or clamped. `WeeklyReviewAnswers.clear(in:)` is the hook a vault reset must call.

### Memoir insights

`Insights/` answers the owner's questions about their own data through `ShadowAI`, ported from the reference's AI worker. `InsightGuardrails` is its output filter with the patterns verbatim on `JSRegex` (crisis first, replacing the answer with the handoff and recording no violation; then verbatim quotes by seven-word shingles, identity and diagnosis, shame copy and claimed mechanic changes, any of which blocks the answer; then suggestions outside the six kinds or naming a quest the data does not hold are dropped), and `InsightPrompt` is the reference's prompt word for word with its reply shape as a schema; the vectors in `Fixtures/guardrails/` pass exactly. `InsightAssembler` builds the context from the owner's records and from replay through `InsightReplaySource` (plain values), and consent decides what is read: the call itself needs `InsightConsent.call` for the provider, journal entries, reflections and reason notes need `journal_reflection_reason`, and health- and activity-class data need `health`, each per provider host, read for the routed host before assembling and again before sending. Without the class nothing of it is read: the activity and restricted stores are not opened and replay is asked for no text. The whole history is sent when it fits the prompt budget, otherwise the widest trailing window from a year down to a week that does. An answer becomes an `InsightRecord` in the store of the highest class its context held (a context with health data keeps its answer in the restricted store), with its suggestions, the data classes it read, the model and the prompt version, and no guardrail status; a suggestion is an offer the owner takes by editing the quest, and the insight path issues no command. `InsightEngine` runs each insight as a `ShadowJobs` job in the main store, which now also holds the AI ledger, consent and jobs (registries v3): `ask` for a question under the app's id, and `runDue(at:)` for the standing question (`InsightScheduleRecord`, 02:00 by default, recording the local date and minute it was set at) on the latest night whose minute has passed and had not yet passed when it was set, so setting it never runs a past night at once, so the Mac worker runs it on time when awake and any device at its next open otherwise, one attempt at a time under the job's lease. Keys come from `InsightJobAddress` and origins from `InsightJobOrigin.json`. Both wait (`waitingForConsent`, `waitingForSpend`) without starting an attempt while the call's consent is missing or a spend cap is reached; an unusable answer or an unreachable model is tried again on a later call, up to three attempts, and an attempt that failed only because consent was withdrawn or the cap reached after it began does not count; a refusal or a blocked answer is not tried again. Each attempt reads consent and data afresh and checkpoints nothing it assembled, and a result already stored for the job ends a repeated step without a second call. The native code deliberately differs from the reference: there are no tiers, so the profile carries no tier and the window comes from the budget rather than the free plan's three months; consent is per provider host; and side quests carry no XP, which is replay's. Like the reference, the quote check reads only `a` to `z` and digits after lowercasing, so it never fires on text in a non-Latin script. The app's replay source is `ProjectionInsightReplay`, which reads the derived rows (the whole hero trail, which `mm_derived_hero_event` now keeps while screens list only `recentHeroEvents`, the Comeback events and shield consumptions in `mm_derived_comeback` and `mm_derived_shield_consumption`) and the command notes, the notes only when text is asked for; catalogue entries carry the day they were earned, as replay keeps no instant. `InsightRequests.listing` gives the latest run of each question or night with its status at a lease instant and the cost of its attempts' calls from the ledger; `InsightEngine.retry(job:)` asks a request again under its next run once it failed for good or was cancelled, and `cancel(job:)` cancels it through the runner.

Handing a job between devices goes through `JobEngine`. `interrupt(job:releasingLease:)` ends this device's run of the job as a crash would (a start or resume under way is waited for first) and answers `JobInterruption`: `interrupted` or `notRunning` when this device keeps the checkpoint, `settling` for a run with a stop mark, which settles instead (`settleStoppedAttempts()`, what an iOS launch runs since it resumes nothing), and `ended` when no attempt of the job is this device's or its attempt here settled; releasing the lease lets another device's automatic attempt start at once, though other devices see the release only once this one next syncs. An iOS expiration handler awaits it with a deadline inside its grace period, then calls `setTaskCompleted`. `interruptedRuns()` lists what this device can resume, with its target and step, and `resumeHere(job:)` continues that attempt from its checkpoint after the consent check; the resumed attempt keeps its start, so beside another device's live attempt it is refused (`runningElsewhere`) unless that attempt would stand down for it, being automatic beside a run started by hand or started later; with nothing to resume it answers `nothingToResume`. `observeRun(attempt:)` streams `JobRunProgress` for a run going here: its step, steps done of those expected, and output tokens received of those expected, counted through `ModelCallHooks.output`, which `EngineStep` sets around each step's calls. Steps expected and tokens received only grow; expected tokens count each finished call at what it produced, each live call at its output cap and each step still ahead on the pipeline's usual `PipelineCourse` at its route's cap, so a repair or a retry adds to them. `requestGeneration(novel:chapter:options:origin:regenerating:)` and `queueReview(novel:chapter:kind:unrestricted:pace:)` ask for a generate or a judge or editorial review behind the gates of `generateChapter` and `requestReview` and start nothing, for a device that leaves the job to the worker (a quick review still answers at once); `run(job:)` is refused (`runningElsewhere`) beside another device's live run by hand, which never stands down, even where a clock behind would stamp the new start first, unless the job already succeeded or was cancelled. `designateWorker(.thisReplica | .none)` writes the vault's `jobs_worker` record through `WorkerRecords.designate` at the engine's lease clock and answers the worker as read afterwards; `worker()` and `observeWorker()` read it as `VaultWorker` (see Jobs below).

`nf-eval` (`NovelForgeEval`, run with `swift run --package-path Packages/NovelForgeKit nf-eval --help`) measures chapters and runs them through plan, generate, review, finalize review, finalize and refresh. A pipeline run calls a model, so it refuses without `--live`, without `NF_EVAL_PROVIDER=anthropic` and `NF_EVAL_API_KEY` in the environment (OpenRouter is refused), and, on a real vault, without an AI consent the author already recorded there. `--live --vault` also needs `--write-vault`: the run writes into the real vault, applying a plan card, writing a draft, a review and an approval as the author, finalizing the chapter and refreshing the Story Bible; those writes sync to the author's other devices and cannot be undone. `--fixture` runs in a throwaway in-memory vault. `--metrics-only` calls no model but still opens a real vault read-write, so pending migrations and projection catch-up are applied.

The report is JSON only. Metrics read a final chapter's canon and any other chapter's draft head (the reference reads one source per run), drop empty bodies as the reference does, and list a body this version cannot read under `skipped`; there is no `--from`, `--to`, `--all` or text report. The fail-open invariant skips the chapters the tool approved itself (`failOpenExcluded`), since its own approval would satisfy it.

### Jobs

Chapter jobs are `ShadowJobs` records in the vault; `Reconcile/Jobs` derives one row per job (`JobEntry`: its key, requester, latest attempt with its replica, step and lease renewal, and the attempts that hold a lease in rank order, each with its expiry and renewal) and the per-novel activity from them. Nothing derived says whether a lease is live: every read model takes a `now` (`LeaseInstant`, trusted time when the vault has it) and decides liveness with `AttemptLease.isLive`, so a lease stamped further ahead than a fresh one plus the skew limit reads lapsed until its window opens; a lease that lapses changes a read with no write, so each of these reads returns `changesAt`, the next moment that happens, for the screen to read again. Schema v6 (`Fixtures/schema/registry-v6.json`) adds `JobSchema.workerEntities`, the vault's `jobs_worker` record; a vault on v5 holds a worker record it receives as foreign and takes it in when it updates. A plan runs on the device that asked for it and every other kind queues for the worker (`NovelJobKind.queuesForWorker`). `WorkerBacklog` lists the vault's jobs of those kinds that read queued at `now`: never started, or every attempt's lease lapsed, and neither cancelled, succeeded nor failed (a failed job waits for Try Again), in request order, with the vault's worker as this replica reads it (`VaultWorker`: none, unreadable, retired, or named, a retired replica followed through `ReplicaDirectory` to its successor); the list is the same on every replica and `isWorkerHere` says whether this one drains it. Two replicas may each read themselves as the worker until the later designation reaches both, and `AttemptVerdict` stands one of their attempts down. `JobPlacements` says where each job stands for this replica: running (the holder's device, named from the replica directory when it can be, its step, renewal and expiry), queued for the requester (a plan) or for the worker, interrupted here (this replica's run whose lease lapsed or was released, with nothing live since), failed, cancelled or succeeded. `JobBacklog` still lists the jobs this replica asked for that no attempt has started.

### Chat

Schema v2 (`NovelForgeSchema.version`; `Fixtures/schema/registry-v2.json` beside v1) adds the synced kinds `nf_chat_session`, `nf_chat_message`, `nf_chat_summary`, `nf_proposal` and `nf_proposal_change`, and registers the ledger kinds `ai_model_call` and `ai_consent` in the vault. `Reconcile/Chat` derives the transcript, window, session state (including the unrestricted lock) and proposal state from them.

`ChatTurnEngine` (`Chat/Engine`) runs a turn: `send`, `answer`, `retry`, `resume`, `cancel` and `interrupt`. It screens the input, compacts the conversation, routes the call through `ShadowAI`, streams the reply, runs up to three lookup rounds and one negation-fix round, stages the change set (`stageTurn`) and appends the reply in one transaction. `resumeInterruptedTurns` runs once when the vault opens: it runs card actions left pending first, clears what this device kept of chats deleted elsewhere, ends turns the author had stopped, resumes the other interrupted turns it can, fails the rest (`CHT_013`), and runs owed chat namings last.

Tables of this device's own, never synced; each is created idempotently by the write that first needs it, read only after a `tableExists` check, and cleared with its owner: chat rows by `ChatLocalCleanup` and `ChatTurnRecords.forgetOrphans`, pending actions by the sweep once the card has none left or is gone:

| --------------------------- | -------------------------------------------------------------------------------------------------- |
| `nf_local_turn`             | One row per turn on this device: its state, session, novel and replica; what resume reads          |
| `nf_local_turn_frame`       | The turn's stream frames, for re-attaching to a running or ended turn                              |
| `nf_local_turn_stop`        | The author's stop mark, so a stopped turn is ended cancelled at launch instead of resumed          |
| `nf_local_turn_basis`       | What a turn was asked and what it settled or staged, which a resume continues from                 |
| `nf_local_turn_call`        | The ledger ids of the model calls a turn began, a call a crash cut off included                    |
| `nf_local_turn_step`        | Which staging transactions of a reply committed, with the notes the reply then carries             |
| `nf_local_chat_naming`      | A session naming owed from its opening message until the naming ends                               |
| `nf_local_pending_action`   | Applied cards whose actions have not settled; the launch sweep runs them                           |
| `nf_local_chat_segment`     | What each reply's turn sent, replayed so the cached prefix holds; other devices send plain history |
| `nf_local_call_inspector`   | The last request of each turn, for the Inspector (newest 20 per session)                           |

Proposals live in `Domain/Proposals`: `ProposalStager` stages a card (anchors, baselines, warnings, supersession), `applyProposal` applies it whole or by selected indexes in one transaction (a baseline mismatch makes it conflicted; the actions `approve_draft`, `finalize` and `advance_volume` each run in their own transaction afterwards), and `undoProposalChange`, `redoProposalChange`, `revertProposal` and `rollbackProposals` reverse it. Every apply and revert goes through typed records and handlers per op family (`Apply/*Handlers.swift`). A passage rewrite that brings in a locked secret its own passage did not give away records the head it was written over as the revision's `leak_hold` (schema v4, `Fixtures/schema/registry-v4.json`); the lifecycle holds that revision as a contradiction until a judge review of it, an approval of it or a later revision. A device still on schema v3 shows that revision as needing review until it updates. The public `ProposalApplyContext(novel:now:)` and `ProposalRevertContext(novel:now:)` take whether unrestricted writing is available from the build (`UnrestrictedWriting.isAvailable`, `false` for now) and expose no way to override it. Unrestricted turns are refused with `AI_024` by `ChatTurnPreparation` and by compaction, and an op that raises a plan to unrestricted is refused by the apply.

### Retrieval

`NovelRetrieval` (`Retrieval/`) is the reference's retrieval service over an index this device keeps and never syncs. It indexes the same kinds of text with the reference's kind strings and keys: each final chapter's prose (its amendment when there is one), chunked as `chunker.ts` does, and one lore row per entity (`character`, keyed by the entity key, text `name`, `notes` and `body`) and per Story Bible page (`bible_doc`, keyed `section/slug`, planner-only pages left out). Unlike the reference, which indexes an entity only when a finalize touches it, pages only when the Bible builder runs, isolated prose never, and removes no lore, the native index covers every live entity and page, holds isolated prose and always follows the current records. `catchUp(novel:)` compares every corpus record's digest in the record index, stamped with `RetrievalCorpus.version`, against the one its source last read; it reads the changed records again, rewrites a source only when the hash of its text (taken before chunking) changed, and drops sources whose record left the corpus, one batch of sources per transaction. It picks up merged records, amends and deletions without any writer calling it, does nothing when nothing changed, and raising the version reads every record again. `searchProse`, `searchLore` (kinds bound as parameters) and `searchProseAndLore` rank with FTS5 BM25 (`unicode61`, diacritics folded) over a MATCH expression that quotes every term of the free-text query, and leave out the chapters isolated now. The tables are `nf_local_retrieval_source`, `nf_local_retrieval_prose`, `nf_local_retrieval_lore` and their external-content FTS5 tables (`*_fts`, kept equal by triggers); `VaultStore.forgetLocalState(novel:)` clears them with the rest of the novel's local state.

Embeddings are optional and never synced. `NovelRetrieval(store:embedders:)` takes an `EmbedderProvider`; `NLSentenceEmbedders` reads the novel's language with `NLLanguageRecognizer` from the opening of its prose (its lore when it has no prose) and uses `NLEmbedding.sentenceEmbedding(for:)` when the system has one for that language (which languages have one depends on the OS and the assets on the device: on the macOS 26 SDK, English, French, German, Spanish, Italian, Portuguese and Simplified Chinese list a revision, Japanese, Korean and Traditional Chinese none; otherwise search is FTS only). `embedPending(novel:limit:)`, run after `catchUp`, embeds the rows that have no vector of the current model in batches of its own writes, at most one vector per row in `nf_local_retrieval_vector` (unit-length little-endian Float32, removed with its row by triggers). Each vector records its model identity (framework model, language, revision, dimension and input recipe); a pass drops the novel's vectors of any other model, so a model change rebuilds and never mixes, and a text the model cannot embed is marked and not tried again until the text or the model changes. Once no row of the novel waits for its model (a failure mark counts as done), a search embeds the query with the model its vectors record (`EmbedderProvider.embedder(forModel:)`, so the text is not sampled again), ranks the novel's vectors by cosine (Accelerate, brute force), applies the same isolation and kinds filters and fuses that list with the BM25 list by reciprocal rank fusion (k = 60). Until then, or with no model, a system model that changed since, or a query it cannot embed, the BM25 ranking stands alone, exactly as without embeddings.

The chat lookups `search_lore` and `search_prose` (`Chat/Lookups`) answer from it in the reference's formats: each lookup round first runs `catchUp`, so an amended sentence is gone from the answer; it never embeds indexed text (no `embedPending`) and embeds only the query, and only once every row of the novel is embedded; a failed index read answers "No lore found." / "No prose found." as the reference does, and only cancellation propagates. `kinds` takes at most 16 entries, which the reference does not cap.

No record write updates the index. `RetrievalUpkeep` (one per open vault, held by the app's `Shared/RetrievalRuntimes`) catches every novel up when it starts and then follows the record index: it reads the rows of the corpus kinds again only after a commit that wrote to `nf_derived_record` (`VaultStore.observeReads(writingTo:_:)`), which the index's own writes never do, so they never wake it: a novel whose final chapters, entities or pages changed, by a local write or a merge, is caught up `RetrievalUpkeep.defaultDebounce` (3 s) after its last change. Each catch-up is followed by embedding in batches of 64 rows; one unit of work runs at a time at background priority, a waiting catch-up goes before the next embedding batch, and no novel is worked on twice at once. A failed unit is logged and tried again 30 s later, the wait doubling with each failure in a row up to 30 minutes, or sooner when the novel changes meanwhile; a retry of a failed embedding batch does not catch up again. On iOS the upkeep stops (between two batches) when the app goes to the background and catches every novel up again on return; on the Mac it keeps running. Embedding a long novel takes minutes; until it is done, search ranks by BM25 alone.

The plan's outline pack adds the reference's `prose_retrieved` and `lore_retrieved` after the catalog (`context-assembler.service.ts` `forOutline`): it searches for the first line of the current volume's objective, reads a failed search as no hits, and both sections are canonical and not required, so the budget drops them before anything else. The pack catches the novel up before it searches, so it never depends on the upkeep. The plan step builds its pack, these hits included, each time it runs and checkpoints only the vetted plan, so a resumed step searches again over the records as they are then, as every other section of the pack reads them again. Retrieved prose never includes a chapter isolated now, even for a planner that reads isolated chapters raw, and that planner's pack screens retrieved text for the hard line with the rest. An empty plan searches nothing.

## ShadowDesignSystem

Shadow UI for Apple: the brand (indigo accent, tinted neutrals, flat opaque content) on native SwiftUI controls, with Liquid Glass for the navigation layer only. Minimum OS 26 on every platform. It contains no user-facing strings.

### Adopting it in an app

1. Depend on it in the app's `Project.swift`: `dependencies: [.shared(.designSystem)]`, then `mise run bootstrap`.
2. Apply the theme and a toast presenter once at the root:

```swift
import ShadowDesignSystem

WindowGroup {
  RootView()
    .shadowTheme()
    .shadowToastPresenter()
}
```

3. Use semantic tokens only (`ShadowColor.textPrimary`, `Spacing.space4`, `Radius.section`), never primitive palette values or literal colours.
4. Keep glass on bars, toolbars, sidebars, menus, popovers and sheets. Content (cards, rows, fields) stays flat on `ShadowColor.surfaceCard`.

The DocC catalog has a getting-started article, the token and contrast reference, the glass rules, and the platform decisions that deviate from the Shadow UI design spec.

### Regenerating tokens

`Design/tokens.json` is the source for colours, spacing, radii, metrics, opacity and elevation. After editing it:

```sh
mise run tokens
```

This rewrites `Packages/ShadowKit/Sources/ShadowDesignSystem/Tokens/Generated/`. Never edit those files by hand. CI regenerates them and fails on a diff. Every text pair in `ContrastTests` must still pass `mise run test:packages`.

## Novel Forge app

`Apps/NovelForge` runs on iPhone, iPad and Mac from one target (`.phoneAndMac`; no visionOS). It depends on `NovelForgeCore`, `ShadowStore`, `ShadowAI`, `ShadowJobs`, `ShadowKeychain`, `ShadowNetworking`, `ShadowDesignSystem`, `ShadowSync`, `ShadowSyncRuntime`, `ShadowSyncCloudKit`, `ShadowSyncS3` and `ShadowAppShell`, which holds its vault model, sync and AI settings screens (see App shell). At launch it opens the vault, one SQLite database at `<Application Support>/<bundle id>/Vaults/Default/vault.sqlite`, off the main actor; a failure shows an error screen with Try Again instead of crashing. In regular width the root is a three-column `NavigationSplitView`: the library, the sections of the selected novel, and the section's screen; compact width (iPhone, compact iPad windows) uses a stack instead (see Novel Forge compact navigation). Unit tests run against a temporary directory, and the app itself uses an in-memory store when hosted by XCTest. Opening goes through `NovelForgeStore` in `NovelForgeCore`.

Each area owns a folder under `Apps/NovelForge/Sources/<Area>/` (`Library`, `Reader`, `Story`, `StoryBible`, `Notebook`, `Chat`) and plugs into the shell through one entry view, `struct <Area>View: View { let context: NovelContext }`, where `NovelContext` holds the `VaultStore` and the novel's id. `Navigation/NovelDetailView.swift` maps a `NovelSection` to that view, so an area replaces only its own folder. The shell keeps one `NovelNavigator` per novel in the environment (`@Environment(NovelNavigator.self)`): `section` is the selected section, `show(_:)` switches to one, `open(_:_:)` replaces that section's own `NavigationStack` path with one `Hashable` route and selects the section (a deep link), and `push(_:)` appends a route within the current section. An area registers `navigationDestination(for:)` for its own route types, and each section's path survives switching sections. A route can outlive its entity (deleted, or removed on another device), so every destination must render a "not found" state rather than assume the entity exists.

A screen that holds text the user has typed registers its flush with `UnsavedWork` (`ShadowAppShell`) (`UnsavedWork.shared.register { … }` returns a token to `unregister` with). The app flushes every registration when the scene leaves the active phase (inside a background-task assertion on iOS), when a window closes, and before quitting on macOS (`applicationShouldTerminate` answers `.terminateLater` until the flushes finish or a timeout passes). A flush should write the text to durable local storage and not depend on the network. Models that carry such state are kept per novel above the section switch (`Navigation/NovelReaders` for the Reader) so a section or novel switch does not discard them.

The Chat area (`Apps/NovelForge/Sources/Chat`) is split into `Composer/` (composer state, mode menu, passage chips and the passage comment sheet), `Cards/` (proposal cards, receipts, question cards and `ChatRevertFlow`, the undo and revert flow shared with `Changes/`) and `Changes/` (Waiting on you tray and the change history with Undo and Roll Back to Here); the transcript, streamed turn, Inspector and history sheet sit beside them. Chat turns run on one `ChatTurnEngine` per open vault, held by `Chat/ChatRuntimes` in the app's environment and shared by every window: the engine alone knows which turns run on this device, so a second engine on the same vault would take a running turn for an interrupted one. When the vault opens, `ChatRuntime.launch()` calls `resumeInterruptedTurns` once and then has every open chat read its turn again. Each novel's `ChatNovelModel` and each chat's `ChatSessionModel` live in that runtime, above the section switch, so a running turn keeps being followed while the Chat section is out of view. The app builds proposal contexts only through the core's public inits. Whether a turn may be written unrestricted is the core's `UnrestrictedWriting.isAvailable`, which the engine enforces and the composer reads to hide the option.

Chapter jobs run on one `JobEngine` per open vault, held by `Jobs/JobRuntimes`, which the app delegate owns for the life of the process (as it owns the AI services and the retrieval upkeep, so a worker Mac runs them with no window), in the app's environment and shared by every window; its lease clock reads the vault's `TrustedClock`, which sync feeds from the storage's time. The engine takes the vault's jobs lock (`<db>-jobs.lock`, an `flock` beside the database that the system drops when the process ends), so a second copy of the app on the same vault runs no job: it shows this device's runs as running in another copy and tries to take the lock over every 30 seconds. `Jobs/JobPlacementPolicy` says what this device starts with nobody asking: a plan runs on the device that asked for it; the other kinds queue for the vault's worker, which only a Mac can be (an iPhone or iPad the worker record names drains nothing); the worker Mac drains the vault-wide `WorkerBacklog` besides its own plans; a Mac that is not the worker runs its own requests of every kind from `JobBacklog`; an iPhone or iPad starts only its own plans and offers Run here for the rest. A screen that asks for a job follows the same rule (`JobRuntime.startsWhenAsked`): on an iPhone or iPad, Generate and Regenerate only request the job (`JobEngine.requestGeneration`) and a judge or editorial review is only requested (`queueReview`, the quick kinds still answer at once), so their lines wait for the worker; approving and finalizing only request their jobs anyway. Try Again and Read Again start the job on the device they are tapped on, as Run here does. When the vault opens, a Mac resumes the attempts it was running (`resumeInterruptedAttempts`), while an iPhone or iPad resumes nothing: it settles its stop marks (`settleStoppedAttempts`) and lists what it can resume (`interruptedRuns`), which its lines offer as Resume. The runtime then starts, one at a time, the jobs the policy gives it (card actions, approvals' finalize reviews and finals' canon refreshes request their jobs in their own writes and are picked up this way), checking each against the queue as it reads at that moment, since the worker may have changed while the job before it ran; a job in the worker's backlog whose last attempt is this device's stopped run is resumed (`resumeHere`) rather than started again, and is started afresh when nothing is left to resume. A lease that lapses changes the backlog with no write, so the queue is read again at its `changesAt`. A start refused for a reason other than consent is tried again only when the queue changes; while the novel's text may not be sent to the AI provider the engine refuses every start before an attempt exists, and the runtime waits until consent is given (from the chapter strip's Review Permission or any other consent sheet). While a job runs here the Mac holds a power activity that keeps it from idle sleep and App Nap.

A screen that starts a run itself hands the handle to `JobRuntime.follow(_:)`, and every followed run is handed to the runtime's `JobRunHost` (`Jobs/RunHost.swift`, given to `JobRuntimes(host:)`) with its progress (`observeRun`), an interrupt that releases the lease, and its end; the host also hears when the scene goes to the background and comes back. On a Mac the host is `ForegroundRunHost`, which does nothing: a run goes on while the app runs. On an iPhone or iPad it is `Jobs/ContinuedProcessing/ContinuedProcessingHost`, which submits a `BGContinuedProcessingTaskRequest` for every run a person started the moment it is hosted, right after the tap that started it, since Apple requires the request to come from the foreground as a result of a person's action (leaving the screen submits nothing). `follow(_:origin:)` says which runs those are (`JobRunOrigin`): a tap (Run here, Resume, Try Again, Read Again, a screen that starts its own run) and a job the drain starts that was asked for since the runtime launched, or after consent was given here, are `.person`; a job already queued at launch and a run resumed at launch are `.automatic` and are never submitted. The request is named `com.shadow.apps.novelforge.job.<attempt>` under the wildcard `com.shadow.apps.novelforge.job.*` that the `continuedProcessing(context: "job")` capability permits, whose one launch handler is registered when the app starts, and uses the `.fail` strategy, so there is never a queued request for the app switcher to drop; iOS 27 submits it with `submitTaskRequest`, iOS 26 with `submit`. Its title names the job's kind and chapter (read from the job's record into `HostedJobRun.target`) and its subtitle the step; its progress is output tokens received of those expected, never falling and never past the total. An automatic run, or one whose request was refused (`.immediateRunIneligible`, `.unavailable` as on the Simulator, or any other), goes on while the app is open, and the run's line says "Keep Novel Forge open until this finishes." When the task expires, by the system or by the person's cancel in the system UI, which the app cannot tell apart, the expiration handler interrupts the run, which releases its lease and keeps its checkpoint for Resume, and completes the task as failed once the interrupt returns or 5 seconds pass; otherwise the task completes with the run, successful only when the run succeeded, also when the run ended before the task started. A run resumed under the same attempt is submitted again under the same identifier. A run the system cut off without a word (the app swiped away) keeps its lease until it lapses and is offered as Resume at the next launch.

`Chapters/ChapterWorkspaceStrip` reads `Jobs/ChapterJobBoard` (`ChapterJobs` with `JobPlacements` in one read) and shows a chapter's status chip and one line per job in flight, stopped or failed: a run on another device with that device's name from the replica directory, its step and when its lease was renewed; a queued job with who it waits for (this device, "Waiting for <worker>", "No Mac runs jobs" or the device that asked for a plan), when it was asked for, and where its last attempt stopped; a run stopped here with Resume, offered only while the engine lists it (also while this device's own lease still reads live, as after an iPhone relaunch, since the engine never lists a run going in this process), its time read as "stopped at" when its lease was released; Stop or Cancel, Run on This Mac or Run on This Device (only while no other device's attempt is live) and Try Again. A Run here or Resume refused for another device's live run names that device.

Waiting on you per novel (`Pending/`): `PendingSnapshot` reads in one transaction the novel's waiting cards, conflicted ones among them, and the applied cards whose actions did not run (`ChatTrayCards`, from `ChatWaitingOnYou`; the chat's tray, `Chat/Changes/ChatWaitingTray`, reads the same), its chapters (`ChapterList`), the ready finalize review of each approved chapter (`FinalizeReviewScreen`) and the jobs of every chapter with one open or failed (`NovelChapterJobs` with `JobPlacements`); `PendingItems.list` turns it into rows with this device's job standing. A chapter lists its draft when it needs review or holds a contradiction, or its Story Bible updates once their read is ready, and its jobs through the chapter strip's `ChapterWorkspaceStatus`, so a row and the chapter's strip always agree: a job waits on the author when it is queued for anyone but this device's own runtime, stopped here with Resume, waiting for consent or failed; a run going on any device, or a job this device starts on its own, is not listed. A job whose chapter has no draft or plan any more is still listed. Order: the cards by age, then their actions, then chapter by chapter in number order, a chapter's draft or Story Bible updates before its jobs, the jobs in request order. Conflicted cards stay listed, where the reference stops listing them, so the author can still apply what fits or discard them. The count is the number of rows. A lease that lapses changes the list with no write, so it is read again at its `changesAt`. On iPhone (compact) it is a home, `PendingView`, reached from the bottom bar's Waiting on you, whose badge counts the same rows from the same `PendingModel`; in regular width the chat's tray adds the chapters' rows (the same `PendingRow`) after its own, collapsed until opened, and a compact chat's tray keeps only its chat rows. A row opens where it is settled through `NovelNavigator`: a card's chat scrolled to it (plan cards with no chat at Plan next chapter), a chapter in the Reader, or the finalize dialog in place; on iPhone a chapter opens above Waiting on you (`openAbove`), so Back returns to it; a job row's Run here, Resume, Try Again, Read Again and Review Permission act on the runtime without leaving the list, and Cancel sits in its menu.

Observe reads with `ReadObserver` (`ShadowAppShell`; `run(_:onValue:)` hands every emitted value to a hook, and an equal value is not republished) and surface failures through `PresentedError` (a localized headline with the error code as detail, never developer text). Markdown prose is rendered by `Shared/ProseView`, which the Reader and the Story Bible share. Strings are per area (`Library`, `Navigation`, `Notebook`, `Story`, `StoryBible`, `Reader`, `Settings`, `Jobs` for the job runtime and chapter strip, `Pending` for Waiting on you, `Generation` for runs and versions, `PlanCard` for Plan next chapter and its cards, `Checks`, `Finalize` for approve, the finalize review and finalize, `Worker` for worker mode and Devices and Worker, `Amend` for amend and summarize, `Export`, `Costs` for run charges and the writer's view, and for chat `Chat`, `ChatComposer`, `ChatCards` and `ChatChanges`, each its own `<Area>.xcstrings`) and are used with `Text(_:tableName:)` and `LocalizedStringResource(_:table:)`; an area adds its own `<Area>.xcstrings` and never edits another's. `Localizable.xcstrings` holds only the vault-opening strings. The sync, key and AI settings screens come from `ShadowAppShell` with their strings.

Each job's screen lives under `Chapters/`, one folder per area, and starts or reads the job through the core:

- Generation and versions (`Chapters/Generation`): options (guidance for the run, and whether and how many times to repair what the checks find), progress while the run streams, the saved versions of a chapter's draft, and an inline compare with a word diff. A run is a job of the core's generation pipeline, its steps checkpointed.
- Plan cards and Plan next chapter (`Chapters/PlanStart`, with the cards in Waiting on you): Plan next chapter asks `JobEngine.requestPlan` for a plan job with the author's line, shows its progress, and lists the plan cards it stages. A plan card staged with no chat shows only here and in Waiting on you; applying it goes through the chat card flow.
- Checks (`Chapters/Checks`): a chapter's findings from the deterministic checks and the editorial and continuity reviews, with the run's progress, Stop and Try Again; the blocking ones must be confirmed to approve over them.
- Approve and finalize (`Chapters/Finalize`): approving a draft requests a finalize review job; the dialog lists its items to accept, edit or skip, and finalizing writes the final chapter and requests a Story Bible refresh job. An approval whose text is out of date is made on the text the author read. Open blocking findings must be confirmed, or the core refuses and asks again.
- Amend, summarize and export (`Chapters/Amend`, `Export/`): amend rewrites a final chapter's text in place (the chapter stays locked), summarize writes a chapter summary with a model call for the author to review and save to the draft, and Export writes the manuscript (Markdown) or a `.novel` package through `NovelExport` (nothing is sent to a model). `.novel` is an exported type, `com.shadow.apps.novelforge.novel` (a zip, declared in `Project.swift`).
- Costs and the writer's view (`Chapters/RunCharges`, `Chapters/WriterInspector`): a chapter's runs with their per-call charges and total, and, on the device that made a call, what the writer was sent (other devices keep no request).

The retrieval index is kept current in the background by `Shared/RetrievalRuntimes` (see Retrieval); one set of the system's sentence embeddings (`AIServices.embedders`) serves it, the job engine's searches and the chat engine's lookups.

Pending OpenRouter costs settle at launch, when a job attempt ends and when a chat turn ends (`CostSettler` in `ShadowAppShell`; one batch at a time, then a 60 s cooldown after a batch that priced nothing).

The cost lookup sends only the generation id with the user's own key; novel-text consent covers content sent to a model, not metered-cost lookups.

### Novel Forge worker mode

On a Mac, the Devices and Worker tab of Settings (`Worker/DevicesAndWorkerView`) lists the vault's active devices from its replica directory, named through `SyncRuntimes.deviceNames`, with this device first, and says which one runs the vault's jobs (none, one that left the library, or a record this device cannot read). Its Run Jobs on This Mac switch drives `Worker/WorkerModel`, which the app delegate owns:

- **On.** `JobEngine.designateWorker(.thisReplica)` names this replica in the vault's worker record; only then does the model ask `SMAppService.mainApp` to open the app at login (through the `LoginItem` seam), keep sync in front (`SyncRuntimes.keepInFront`, so the 45 s polls go on with no window), hold a `ProcessInfo` activity that keeps the windowless Mac out of App Nap while allowing idle sleep, and show the menu-bar item. A failed designation leaves worker mode off and says why.
- **Off.** The record is cleared (`designateWorker(.none)`) only when a fresh read still names this Mac; the login item is unregistered, sync goes back to following the scene and the activity and menu-bar item go. With no engine to write through (the library did not open, or another copy holds its jobs) it still turns off here at once and leaves a marker (`com.shadow.apps.novelforge.worker.clear-pending`): the next vault attached clears a record that still names this Mac, and nothing turns worker mode back on until it has.
- **The record decides.** The job runtime drains `WorkerBacklog` by the record, not by the switch, so the model follows `observeWorker()`: another Mac named later, or a record naming none, turns worker mode off here with a notice saying who took over; a record naming this Mac (a retired replica's successor, or defaults lost) turns it on without touching the login item; an unreadable record changes nothing. Each emission that would change the mode is read again first, since one may predate this Mac's own last write. The preference (`com.shadow.apps.novelforge.worker.replica`, per device) keeps the replica it was turned on as: a library opened in place of that one turns worker mode off instead of naming this Mac on its own. Two Macs turned on together both drain until the later designation reaches them (see Jobs).
- **Login item.** It is registered only when the user turns worker mode on (or taps Open at Login after removing it in System Settings), never at launch. Requires Approval offers Open Login Items Settings (`SMAppService.openSystemSettingsLoginItems`), and the status is read again when the app becomes active. `SMAppService` needs a signed app: a build without a team gets a refusal or Not Found, shown as "This build can't open at login" while worker mode itself keeps working.
- **No window.** While the preference is set, the library window is not opened at launch (`defaultLaunchBehavior(.suppressed)`; a Dock click on the running app or Open Novel Forge opens one), and the delegate opens the vault and starts sync, the job runtime, the retrieval upkeep and the OpenRouter model list itself; the app does not quit after its last window closes. Launching the app by hand while worker mode is on therefore shows only the menu-bar item until a window is asked for. On wake from sleep the worker counts as a foreground for sync (at most once a minute), so it hears of takeovers and new jobs at once.
- **Menu bar.** `Worker/WorkerMenuBar` is a `MenuBarExtra(isInserted:)` shown while worker mode is on, drawn by the system: its status (`WorkerMenuStatus`: no jobs to run; the oldest run going here with its kind and step from `observeRun`, and how many more; or waiting for the library, another copy of the app, consent or an unreadable record), Open Novel Forge (brings a library window forward or opens one), Devices and Worker Settings, and Quit Novel Forge.
- **Under XCTest.** `WorkerModel.live` uses a throwaway defaults suite and an inert login item, so the tests never touch this Mac's preference or login item.
- **Quitting.** Quitting the app, from the menu or otherwise, stops the job runtime (`JobRuntime.stopBeforeQuitting`, at most 3 s): its queue stops draining, nothing starts or resumes, a start under way is waited for, and every run going here is interrupted with its lease released before the final upload sends the release, so another device may take the job over at once; the checkpoint stays and the next launch resumes it unless another device took it. The worker record stays: quitting stops the worker until the app opens again, it does not turn worker mode off.

An iPhone or iPad never designates itself: the AI settings sheet links the same page read-only, which says which Mac runs jobs.

### Novel Forge compact navigation

`NovelForgeShell` reads the horizontal size class (`NovelLayout`): regular width (Mac, regular iPad windows) keeps the three columns; compact width (iPhone, compact iPad windows) runs `Navigation/Compact`, a two-column `NavigationSplitView` that collapses to a stack, library first, whose detail is one `NavigationStack` per novel (`CompactNovelView`) rooted on Chat. A selected novel opens on Chat. A bottom bar offers Chapters (pushes the Reader section onto the chat stack, chapters push on it in turn, so Back from a chapter goes to the list and then to Chat), Waiting on you (its badge counts the rows of `Pending/PendingView`, the destination) and a More menu with Story, Story Bible, Notebook and Overview.

`NovelNavigator` serves both layouts through the same calls (`show`, `open`, `push`, `pop`, `isAtRoot`), so deep links work in both: in compact it keeps a single `compactPath` of `CompactStop`s and routes instead of one path per section. `openAbove(_:_:)` is `open` that, in compact, keeps the stops already shown beneath the section, and Back to them shows their section again; in regular width it is `open`. A size-class change (iPad multitasking, Stage Manager) keeps the selected novel and section; the routes pushed above the section are dropped, because a `NavigationPath` cannot be moved between the two layouts. Screens in a compact stack must not rely on `navigator.paths`; ask `navigator.isAtRoot(_:)`.

### Novel Forge sync wiring

`SyncRuntimes` (`ShadowAppShell`, made with `SyncRuntimes.live(identity: .novelForge)`) holds one `SyncRuntime` per open vault in the app's environment, owned with the `VaultModel` by the app delegate so a silent push can open the vault and sync it with no window. The vault opens with `SyncEngine.wallClock(preferring:)` of the model's one `TrustedClock`, which the runtime is handed too. Launch starts the runtime; the scene phase calls `foreground()` and, on iOS inside a background task (`SyncBackgroundWork`), `background()`; on the Mac the app or a window becoming main counts as a foreground at most once a minute, and quitting sends what is unsent for up to 3 s. Every commit that logs a change (`VaultStore.loggedChanges()`; uploads and remote applies do not) calls `localWrite()`, a push calls `changeNotice()` for up to 25 s, and a vault opened in place of another, or closed, shuts its runtime down. While XCTest hosts the app nothing syncs.

`SyncWiring` builds the `SyncStartupEnvironment`: the files under `<Application Support>/<bundle id>/Sync/` (`location.json`, the first-unlock probe, CloudKit's index and engine state), `SyncSecureStores.keychain(app: identity.id, sharedAccessGroup:)` (`com.shadow.apps.novelforge`), providers (a local folder through its security-scoped bookmark, kept open for the life of the process; S3 with its keychain credentials; OneDrive and Google Drive refused until they can sign in) and account checks (iCloud binds the user record name). Restricted capabilities are known from the `ShadowCapabilities` Info.plist dictionary, which `Project.app` writes only for the entitlements it emitted (`CloudKitContainer`, `PushNotifications`, `SharedKeychainGroup` with `$(AppIdentifierPrefix)` expanded by Xcode): iCloud is offered, attached on first use and its one `CKZoneClient` made only when both the container and pushes are there, remote notifications are registered only with pushes, and a shared group whose prefix was not expanded leaves the keys in the app's own group. A build without a team therefore never touches CloudKit, and only a folder or S3 can be chosen; on the Mac such a build cannot sync even there, since the data-protection keychain refuses to add or delete any item, synced or this-device, without an application identifier (`errSecMissingEntitlement`, seen from the hosted tests and an ad-hoc-signed probe), while its reads find nothing. The start-up probe therefore reports `keychainUnavailable` instead of a vault awaiting its key: an attached vault stops before its provider is made and a vault met on first use before a location is saved, both shown by the status indicator as "Sync needs a signed build"; an explicit create or join throws `SyncStartupError.keychainUnavailable` and saves no location, and saving S3 credentials throws `SyncCredentialError.keychainUnavailable`. The sync settings word those errors as "cannot sync" and offer nothing to connect. A team-less build is a development convenience, not a sync target. The keychain tests under `Tests/Keychain` run in the app host and skip, with that reason recorded, when the host lacks the entitlement; with `TUIST_DEVELOPMENT_TEAM` set they run for real.

A vault that cannot be opened before the device's first unlock (`FirstUnlockProbe`) waits as `locked` and opens on `protectedDataDidBecomeAvailableNotification` or Try Again. `SyncStatusIndicator` sits in the library sidebar's toolbar: hidden while sync is off, otherwise up to date, syncing or attention needed, with a popover saying what is wrong and what it stops (`SyncIndicator`, strings in the shell's `Sync.xcstrings`); it never blocks anything.

### Novel Forge sync settings

`SyncSettingsView` is the Sync tab of the Mac Settings window (`Settings/NovelForgeSettingsScene`), a sheet from the sync indicator's popover, and a page linked from the AI settings sheet on iPhone and iPad. It shows where the library syncs (storage, location, library id and status) and turns sync on through `SyncConnectModel`: iCloud only in a build signed for it, creating or joining on its own after discovery; a folder through the file importer, kept as a security-scoped bookmark (`LocalFolderAccess`; a stale bookmark is renewed and saved over the attached location unless a move is recorded), never inside the app's own data; S3 through a form whose keys are first checked by `probeConditionalWrites()`, then saved to the keychain with the probe's answer kept in the settings (cancelling puts back what it saved); OneDrive and Google Drive listed but disabled until Novel Forge has an app registration. Every storage but iCloud asks explicitly for "Create a Vault Here" or "Join the Vault Found Here", and a newer or unrecognized location only explains itself. Disconnect is confirmed in the page and keeps the library and the synced copy. Move to Another Storage runs `SyncRuntime.moveVault` into an empty location; a move or follow that stopped shows Continue and Abandon, and a move notice from another device offers Follow Move (a folder is picked again on this device, S3 reuses keychain keys) or Stay Here. A build whose keychain refuses writes with `errSecMissingEntitlement` (a Mac build without a team) says it cannot sync and offers nothing to connect; it learns that from the runtime (`SyncRuntime.keychainUsable()` before anything is attached, the `keychainUnavailable` phase and errors after). Cancelling a pass, or leaving the page while it is idle, puts back every S3 key the pass saved that neither the attached location nor a move in progress uses. On the Mac, `SettingsTabs` is shared by the app's scenes, so AI Settings and Sync Settings buttons each open their own tab. Keys and Devices is linked from the page's Keys section; while the library waits for its key, the page starts with that state and a way there.

### Novel Forge key screens

`SyncKeysView` (Keys and Devices, in `ShadowAppShell`) is pushed from Sync Settings and, while this device lacks a key (`awaitingKey`, `writingKeyMissing`, `keysMissing`), opened from the sync indicator's popover: as a sheet on iPhone and iPad, in the Sync tab of Settings on the Mac (`SettingsTabs.syncKeys`, cleared by the Sync Settings button and when the Settings window closes). `SyncKeysModel` reaches keys only through `SyncKeyServicesSource`, which holds the runtime's `SyncKeyAccess` and, when a call throws `unavailable` (after a move, or a disconnect and reconnect), fetches it again and repeats the call once for the same vault; a vault replaced meanwhile, or sync turned off, stops the flow on screen and says so. Flows run inline in the page and end when it goes away, taking the phrase, typed words and any exchange with them.

- **Waiting.** A device with no key shows "Waiting for this library's key from your other devices" with Enter Recovery Phrase and Scan from Another Device. It asks the runtime to look again (`SyncRuntime.foreground()`) when the scene comes to the front and every 30 s while the page is on screen, and says so when the key arrives.
- **Offer.** While this device holds the key and the library has no phrase, Sync Settings and the indicator's popover offer to set one up (`RecoveryPhraseOffer`); Set Up Recovery Phrase opens the page straight into setup, and Not Now turns the offer down for that library on this device (`com.shadow.apps.novelforge.sync.recovery-offer-declined.<vault id>`).
- **Recovery phrase.** A device holding the key shows whether a phrase is set up and offers to set one up or make a new one (confirmed first: the old phrase stops working). The 24 words are shown once, from the runtime's `PendingRecoveryPhrase`, with no copy button and no text selection, hidden while the scene is not in front or (iPhone, iPad) the screen is captured; saving needs the three words the runtime picked typed back. The app keeps only the phrase's recipient id, in the user defaults under `com.shadow.apps.novelforge.sync.recovery-recipient.<vault id>` (`RecoveryPhraseRecord`, also written after a recovery by phrase), and shows "replaced on another device" when `RecoveryStatus.standing(ofRecipient:)` says so.
- **Recover by phrase.** The words are typed or pasted (`RecoveryPhrase` normalises case, spacing and Unicode form); a wrong word count, an unknown word, a bad checksum, a phrase that opens no copies here, copies that fail their check and keys that open no file yet each have their own message.
- **QR exchange.** The device that needs the key shows its request (`CIQRCodeGenerator`, with Copy Code as Text), then scans the answer and asks for the six digits the other device shows; its own code is never shown, so the user cannot confirm by copying it from the same screen, and a mismatch ends the exchange with nothing added. The holder scans the request, shows its answer, and reveals its code (`revealConfirmationCode()`) only after the user says the other device scanned it. Scanning uses VisionKit's `DataScannerViewController` where it is supported and allowed on iPhone and iPad, an `AVCaptureMetadataOutput` session on the Mac, and on every device a field for the code's text (typed or pasted); a denied camera, a device that cannot scan and a Mac without a camera each say so. Whether a failed scan keeps the exchange waiting comes from the request itself (`SyncKeyRequest.isAwaitingResponse`): a code of the wrong kind, one that cannot be read or an answer to another request leaves it waiting; another library's answer, or one that fails its check, ends it.
- **Devices.** Each key of this device's ring with the devices that have shown they hold it (`SyncKeyAccess.keyHolders()`), by the name in the replica directory or manifest; the page makes no claim about iCloud Keychain. It is read when the page opens, after a flow and when a key arrives, not on a status change or a key check, since it fetches a file per device; the page shows before it answers.

## Memoir app

`Apps/Memoir` runs on iPhone, iPad and Mac from one target (`.phoneAndMac`). `MemoirAppDelegate` owns the vault (`MemoirVaultModel`, the shell's `VaultModel` over `MemoirVaultOpener`, opened with the trusted clock), its sync and `AIServices.memoir()` for the life of the process, as Novel Forge's delegate does: pushes are registered only when `ShadowCapabilities` allows them, the Mac syncs on activation and uploads before quitting, and `MemoirDayTurns` runs the open vault's `ProjectionDayTurns` (the projection built with `MemoirReconciler(appVersion:now:deviceZone:)` on the trusted clock), restarting it on a return to the foreground and when the system clock or the device's zone changes (`significantTimeChangeNotification` on iOS, `NSSystemClockDidChange` on the Mac, `NSSystemTimeZoneDidChange` on both), so the derived rows walk to each midnight of the account's zone. Every destination and route view takes one `MemoirScreenContext` (`init(context:)`): the stores, `MemoirWriter` and the account's day (`today()`, `observeToday()`, with the zone's `AccountZone.Source`). `MemoirWriter` is how screens write, each call one main-store write whose commands are stamped with the clock in force on the account's day, read inside that write: `issue(_:text:)`; `issue(_:text:creating:)` for a command and the general-class record it names (journal entries, meals, side quests, meal presets, quests; any other class is refused as `recordNotGeneral`); `write { issuer, transaction in … }` for records and commands together; and `quickLogs` (weights) and `metrics`, MemoirCore's writers wired to the same source. Failures are `MemoirWriteError`, shown through `WritingErrors.presented(_:)` in the reference's wording (`Writing.xcstrings`); a cancelled write is `.cancelled` and shows nothing. `MemoirSyncRoutes` hands sync the main store as the primary and the activity and health stores as the routes `activity` and `health`, as `MemoirSyncRouting` decides: on iCloud only main, plus activity while the owner's Activity setting is on; elsewhere all three. The setting (off by default) is the Activity section of Sync Settings (`ActivitySyncModel`): turning it on writes `HealthSettings` and reroutes; turning it off stops sending activity at once (at most the one upload already in flight finishes, through `SyncRuntime.stop()`, which halts the engine) and leaves every activity record on the device, out of backups. The insights' consent disclosures are `ConsentDisclosure.memoir` (the call, journal and health classes); no route has a request guard. The Mac has a Settings window with AI and Sync tabs; on iPhone and iPad the Settings destination reaches them through `MemoirSettingsLinks`. The sync indicator sits in the navigation shell's toolbar. `ReminderScheduler` (`Sources/Reminders`) follows the open vault beside the day turns: it observes `ReminderReads.observePlan` with a limit of 60 (headroom under the system's 64 pending requests), applies `ReminderPlan.diff(against:)` to the pending requests (only ids under `Reminder.identifierPrefix` are removed), writes the words in the owner's locale (`ReminderCopy`, `Reminders.xcstrings`; money exact from minor units) and pins each trigger to its instant. It restarts when the clock or the device's zone changes and on a return to the foreground. "Remind me on this device" (`com.shadow.apps.memoir.reminders.on-this-device`, on by default only on iPhone) is kept per device; turning it off withdraws every request, and permission is asked only while it is on and the plan holds a reminder. A closed vault leaves its requests pending; `withdrawAll()`, for a deleted vault, removes its pending and delivered ones. Settings shows the permission, the quest reminders a replay halt pauses (subscription reminders continue) and the reminders the limit leaves out. `MemoirInsights` (owned by the delegate, in the environment) holds the vault's one `InsightEngine`; insights start only in the foreground (an attempt under way when the app leaves it is not interrupted on purpose; iOS may suspend it, and it resumes at a later launch): the first time a vault is active it resumes this device's interrupted attempts, and every return to the foreground runs the standing question's due night. It holds the shell's `CostSettler` for the vault: leftovers are priced when the vault is followed, and pending calls after each foreground run and after each attempt the Ask screen starts or cancels. The Ask screen (`AskModel`) asks one question at a time, holds it for the call's consent through the shell's consent sheet, shows and changes the journal and health consents, cancels and retries (a queued request, whose attempt may have run on a device that went away, can be asked again once its lease has lapsed; only a running one blocks a new question), lists the answers with the cost of each and the spend against the caps, sets or turns off the nightly question, and links each suggestion to the quest builder or the quest, never applying it.

Money (`Sources/Money`, strings in `Money.xcstrings`) ports memoir-web's finance screens: the Money screen (the range's spending against the same stretch before, this month's budget, the subscriptions' monthly cost and the average day, the expense list with search, range and category filter, where it went, and the subscriptions and currency rails), the full expense list, an expense's detail with its edit history, the expense form, subscriptions with their form, and categories. Each reads `MoneyReads` through a `MoneyFeed`, restarted when the account's day, the range, the search or the category changes. Amounts are typed in the owner's locale and read only through `AmountInput` with `AmountFormat(locale:)`, which refuses digits past the currency's ISO 4217 places inline, and are shown from minor units as a `Decimal` with exactly those places in the locale's currency format (`MoneyText`). Expenses are written only through `ExpenseEdits` inside `MemoirWriter.write`; a saved expense's currency is fixed; deleting one keeps its words on the screen so Undo writes it again under the same id (not offered for an expense with a receipt or one a subscription cycle wrote). Subscriptions are written as their record and its `subscription.create`, `.update` or `.delete` command together (`SubscriptionWrites`), a due cycle is confirmed through `CommandIssuer.confirmCycle`, and archiving a category issues `category.setArchived` and keeps the flag in its `ExpenseCategoryRecord`. An expense still waiting for a rate shows "Rate pending" and is counted apart from the totals. The budget is set in Settings; before the vault has a base currency, Money says so and links there.

Reflect (`Sources/Reflect`) shows `ReflectReads` and nothing else: History pages twenty records at a time, filtered by one kind and searched as the core matches (names, merchants and category labels only; a built-in category is searched by its stored label, or by its key when it has no record, so `Subscriptions` finds nothing while `subs` does, as an archived built-in keeps the label it was archived with), with a record's details beside the stream on a wide screen and pushed as `ReflectRoute.record` on a narrow one, each opening the screen that owns it. Insights reads 30 days, 90 (the default) or the year; its longest streak is the longest best run of any quest in `QuestList`, never replay's. Weight and metrics are read for `ReflectBody.onThisDevice` (activity and health, since every device opens both stores) and a body section says which classes it did not read. The Weekly Review's answers and completion go through `WeeklyReviewAnswers` only: they stay on the device, issue no command, start over when the day turns into a new week, and a draft of a week that has ended is never written, since a write for one week clears the others.

The Log screens (`Log/`) read `LogReads` through `LogStreams.following`, which restarts a read when the account's day turns. Journal entries, meals, meal presets and side quests are written with `MemoirWriter.issue(_:text:creating:)` (preset edits and deletions through `write`), weights through `quickLogs.saveWeight`, which asks before replacing a weight and replaces without asking only one this store's replica wrote last that no `weight.save` names (an unreadable `weight.save` counts as naming it), and metrics through `metrics`, each day in the store of its class. Typed numbers are read exactly by `DecimalInput` in the owner's locale (water in litres, durations in hours); weights are shown in the device's own unit (`WeightUnitPreference`). A threshold offer is completed only through `QuestActionsModel` after the owner accepts it. Apple Health (`Health/`) is read on iPhone and iPad only, when `ShadowCapabilities.HealthKit` is `YES` and `HKHealthStore.isHealthDataAvailable()`: `HealthKitReader` implements MemoirCore's `HealthReader` over a `HealthSampleSource` (`HealthKitSampleSource.shared`, one long-lived `HKHealthStore` and the only HealthKit importer, with statistics queries for totals and anchored queries for samples), `HealthReadingModel` asks for a type when the owner turns its metric on, claims the vault's reader designation (asking before taking it from another device) and gives it up with the last metric, the chosen metrics are this device's defaults (`HealthPreferences`), cleared once another device holds the role, and `MemoirHealthImports` runs `HealthImport` when a window opens the vault, when the scene becomes active and when protected data becomes available, never from a silent push. Background delivery is not used.

Receipts (`Sources/Receipts`, strings in `Receipts.xcstrings`) port memoir-web's receipt photo and viewer and memoir-server's receipt structuring. A receipt is added only while an expense is first saved, as the reference allows and the core keeps a saved expense's receipt fixed: the document camera (VisionKit, where the device has one), the photo library or a file gives an image that `ReceiptPhoto` re-encodes as an upright JPEG of at most 3,000 pixels a side and 8 MiB, without its metadata, held in memory until the form saves. `ReceiptWrites` then puts it with `VaultBlobs` on the main store and only afterwards writes the `ReceiptRecord` naming the `BlobID` verbatim, the expense naming the record and, when the owner used the reading, `receipt.scan` (the expense's source is then `ocr`) in one main-store write, so a failure never leaves a record naming a missing image (a kept image nothing names is removed by the kernel in time). Reading a receipt recognises its text on the device (Vision's `RecognizeDocumentsRequest`, then `RecognizeTextRequest`), and only that text, cut to the reference's 8,000 UTF-16 units, goes through the vault's `TaskRouter` (helper task) under the `memoir.receipt_text` consent, with the reference's structuring prompt plus the currency and the built-in category keys; a reply whose total is off the reference's pattern offers nothing, and a reading in a currency the form can't take, or whose total doesn't fit the currency's places, offers no total and never switches the form's currency. The owner reviews what was read, fills the form from it and saves it themselves. `ReceiptViewer` shows this device's copy or fetches it through the primary `SyncRuntime.fetchBlob`, with states for a download, a missing or damaged copy, no copy on this device and a key this device lacks, zooms by pinch, double tap, toolbar or VoiceOver, and shares the photo as `Receipt.jpg`.

## Catalog app

`Apps/Catalog` is a gallery of every component and token page in light and dark, with the presentation and device-screen demos. It is also the pipeline's smoke test and the subject of the screenshot harness. Run the `Catalog` scheme from the workspace, or `Catalog -list-components` to print the page ids.

Launch arguments: `-component <id>`, `-appearance light|dark`, `-scroll <0..1>`, `-screen <name>`, `-present`, `-animated` (keeps animations on for a deep link, which otherwise disables them).

### Screenshot harness

```sh
mise run screenshots -- --platform iphone,macos --component Button,Card --appearance both
mise run screenshots -- --help
```

Output goes to `scratch-pad/shots/latest/<platform>/<id>-<appearance>[-s<percent>][-<screen>][-presented][-landscape].png`.

| Option                             | Effect                                                                                                       |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `--platform iphone,ipad,macos`     | Platforms to capture (default all)                                                                           |
| `--component <id>,…`               | Page ids from `Catalog -list-components` (default all)                                                       |
| `--appearance light,dark,both`     | Appearances (default both)                                                                                   |
| `--scroll <f>,…`                   | Scroll positions from 0 to 1 on scrolling pages, for example `0,0.5,1`                                       |
| `--screen <name>,…`                | Sub-screens of pages that have several, such as `library`, `today` and `stepup` on iPhoneScreens             |
| `--present`                        | Open the page's sample sheet, alert, popover, toast or palette before the shot; files get `-presented`       |
| `--orientation portrait,landscape` | iPad orientation. Landscape runs a UI test (`CatalogUITests/CatalogShotTests`)                               |
| `--content-size <name>`            | Simulator Dynamic Type size, such as `accessibility-extra-extra-extra-large`; the next default run resets it |
| `--out <dir>`                      | Output directory                                                                                             |
| `--skip-build`, `--keep-booted`    | Reuse the last build in `scratch-pad/derived-data`; leave simulators booted                                  |

How it captures:

- iPhone and iPad use `simctl io screenshot` on iOS 26.5 simulators. Each shot is retaken until two consecutive frames match.
- iPad landscape runs the iOS UI test, which rotates the device and screenshots with `XCUIScreen`. The harness writes the shot list to a file and passes its path in `CATALOG_SHOT_PLAN`; the test skips when the variable is absent.
- Mac needs no permission: the app composites its own windows into a PNG (`-snapshot <png>`), without Screen Recording access.

Simulators and the window server require running outside any command sandbox. Inside one the run hangs.

## Testing

```sh
mise run test:packages                      # shared packages with SwiftPM; no generation needed
mise run test:apps                          # tuist test --skip-ui-tests
tuist test Catalog --platform macOS --no-selective-testing
tuist test NovelForge --platform macOS --no-selective-testing
tuist test Memoir --platform macOS --no-selective-testing
```

- `mise run test:packages` covers `ShadowKit`, `NovelForgeKit` and `MemoirKit`. Property tests print their seed on failure; rerun it with `replay(seed:)` from `ShadowTestSupport`.
- NovelForgeKit property tests spread their iterations over the cores, at most one per processor (`forAllConcurrently`). Unset, `ProjectionProperty` runs and the record helpers (`ProjectionProperty.iterations(full:)`) run half their iterations; plain `forAll` is never reduced. These keep every iteration at the default because a coverage gate or a kill needs them: the three-replica domain property, the plan-world reach test, the Notebook projection property and the Volume state property. `NOVELFORGE_PROPERTY_SCALE=n` runs `n` times the full iteration count of every property: 1 is full strength and is what CI runs (`.github/workflows/ci.yml` sets it), `NOVELFORGE_PROPERTY_SCALE=4 swift test --package-path Packages/NovelForgeKit` is the deep run for mutation checks, and unset is the local default (half). `NOVELFORGE_DOMAIN_REPLAY=<seed>` replays one domain case.
- Every suite takes a `TestTimeLimit` tier (defined once per test target) instead of a literal limit: `quick` 5 minutes for unit suites, `standard` 10 for store, replica and derivation suites, `property` 20 for property, interleaving and concurrency suites. They are hang detectors with headroom for a loaded machine, not performance budgets; polling helpers wait up to two minutes and return as soon as the condition holds.
- Three suites under `Tests/NovelForgeCoreTests` carry the chapter work's done-when: `ChapterInterruptions` (plan to canon killed at every crash seam of every pipeline, and resumed, with the same footprint as an uninterrupted run), `ChapterReplicas` (two replicas alternating steps, both asking at once, running apart, and running here after a lease lapsed) and `FinalizeIdempotence` (finalizing again, by relaunch, job, card or a second device, writes the same values). `HandOff` simulates handing jobs between a phone and a Mac: the phone asks and the Mac worker writes, the phone alone interrupted before every step and mid-call and resumed, two Macs that each believe they are the worker, the Mac taking over a released run and standing down when the phone resumes, a release not yet synced, clock skew within the limit and a retired worker; each ends with the footprint of the same work done on one device.
- What only real devices can show (continued processing, the Mac worker and its login item, the phone and Mac hand-off) is checked by hand with `Docs/hardware-checklist-phase8.md`, which also lists the known follow-ups.
- Pass `--no-selective-testing` when verifying a change: Tuist otherwise skips targets it considers unchanged.
- CI runs `swift test` for the packages, then `tuist test` per platform: iOS with UI tests, macOS with `--skip-ui-tests`, and visionOS with `--skip-ui-tests` on `Catalog` only (the new apps have no visionOS destination).
- Swift Testing tests that resolve `Color` or `Font` must be `@MainActor`.

## Conventions

- Swift 6 language mode with complete concurrency checking; `ExistentialAny` and `MemberImportVisibility` are on everywhere.
- App targets default to `MainActor` isolation; library modules do not, except `ShadowDesignSystem`.
- Swift Testing (`import Testing`) for all tests; test names start with `should`.
- Errors crossing a module boundary conform to `ShadowError` and are thrown with typed `throws(...)` where the set is closed.
- Minimum OS 26 on every platform, set once in `Organization.minimumOSVersion` and the package manifest.
